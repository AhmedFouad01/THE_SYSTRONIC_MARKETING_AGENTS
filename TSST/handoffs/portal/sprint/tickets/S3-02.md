## Design

### 1. One word per job (server read model, `src/service/dash/job-word.ts`)
`JOB_WORDS = ["changes_requested", "waiting_on_client", "pending_review", "scheduled", "posted", "approved", "delivered",
"planned", "in_progress", "on_hold"]`. `JobWord = { word, days?: number, count?: number, date?: string }`.

`jobWordsOf(db, env, world, brand, today): Promise<Map<jobId, JobWord>>` for every job of the brand that is not archived
or deleted; items = the job's items that are not withdrawn. First rule that holds wins:
1. `delivered`: job status delivered.
2. `changes_requested`: an item has an owed client "changes requested" (S3-01's rule); `days` = days since the oldest one.
3. `pending_review`: an item's current version has no team decision or a pending one and is not sent; `count` = those
   items. Above "waiting on client" on purpose (changed 2026-11-07 after the build found the first draft's order
   contradicted SAMPLE-STATE § 4): November posts with 3 pending and 2 waiting reads "Pending review · 3 items", and
   such a job is not a Needs attention row.
4. `waiting_on_client`: a visible item (`clientReviewItem`) has no client decision or a pending one; `days` = days since
   the oldest `sent_at ?? created_at`.
5. `scheduled`: a post item's life is scheduled (organic) or in_review (ad); `date` = the earliest `publish_on` not before
   today, else the earliest (an ad's day is `ad_start`, else `publish_on`, as the code already counts ads).
6. `posted`: a post item's life is posted / active / completed; `date` = the latest publish date.
7. `approved`: every visible item carries a client approval and at least one visible item exists.
8. otherwise the job's own status: `planned`, `in_progress` (also `in_review` maps here), `on_hold`.

The waiting and owed reads move out of `clientHealth` into one exported `clientReviewFacts(db, world, brand, today)`
(per item: id, job, waiting days | null, owed days | null) that both `clientHealth` and `jobWordsOf` call, so the health
word and the job words can never disagree. `clientHealth` keeps its signature and its tests.

### 2. `GET /api/v1/client` gains `overview`
```
overview: {
  words: Record<jobId, JobWord>,                     // every non-archived job of the brand
  attention: AttentionRow[],                          // see block A; sorted as listed there
  direction: { stage: FunnelStage | null, campaign: { id, name } | null,
               milestones: { done, total }, next: { id, title, due } | null },
  activity: { signed_in: { person, at } | null, viewed: { person, title, job, at } | null },
}
AttentionRow = { kind: "job", id, job, title, project_name, type, items, word: JobWord }
             | { kind: "milestone", id, title, due, days }                       // overdue by `days`
             | { kind: "payment", package_id, package_name, due, amount, currency, days }  // days < 0 = overdue
```
- `attention` rows: jobs whose word is `changes_requested` or `waiting_on_client`; milestones not done with `due < today`
  (every scope of the brand, not archived); the primary package's `next_payment` when unpaid and due within 14 days or
  overdue. Order: overdue payment, `changes_requested` (days desc), `waiting_on_client` (days desc), overdue milestones
  (days desc), a due payment. The count of the block = rows.
- `direction.campaign` = the first project by `order` that is not general, status planned / active / paused, with a goal;
  `stage` = its goal. `milestones` = that project's milestones (scope project) done / total; without a campaign, the
  brand's milestones of every scope. `next` = the earliest milestone not done (every scope), overdue included.
- `activity` = the latest `sign_in` entry and the latest `view_job` entry of the brand (`listActivity`, two reads).
- `docs/DASH-API.md`: an S3-02 section with the shape, the word rules and the attention rules; the route table is unchanged.

### 4. The Overview tab: five read blocks, no create button inside any block
Grid `.overview`: two columns at desktop (A spans both), one column on the phone. Every block is a `Card` with a title row
(`card__head`: title + count or one link). Words from `copy.th.client.overview` (EN) and the same keys in
`copy/ar/copy.ts` (AR, from SAMPLE-STATE.md § 9 and mockup 01).

A. **Needs attention** `<count>` (span). One row per `attention` row: title, sub line, chip, one `Open`.
   - job: title "Winter catalog · v2" (title; the version is already in the title), sub "Winter campaign · Design · 1 item",
     chip `Changes requested · 4 days` (`chip--changes`) or `Waiting on client · 1 day` (`chip--waiting-client`); Open →
     `jobHref`.
   - milestone: title, sub "Milestone · due 2 Nov", chip `Overdue · 3 days` (`chip--overdue`); Open → `?tab=plan`.
   - payment: title "Payment due 15 Nov · 5,000 EGP", sub "Starter Pack", chip `Due · in 10 days` (`chip--due`) or
     `Overdue · 2 days` (`chip--overdue`); Open → `?tab=settings`.
   - empty: count 0 and one line with the cyan dot (`dot--ok`): "Nothing stuck. Next milestone Showroom shoot · 12 Nov."
     (the second sentence only when `direction.next` exists). AR: "مفيش حاجة واقفة".
B. **Direction** · link `Plan` → `?tab=plan`. `kv` list: Stage (stage chip; "—" when none), Campaign (name, a link to the
   project page; "No campaign yet" when none), Milestones "4 of 7 done", Next "Showroom shoot · 12 Nov" ("—" when none),
   then the `.milestones` dots (done = filled). No goal / result line (Sprint 5).
C. **This month's package** · link `Settings › Package` → `?tab=settings`. From `package` (the primary subscription):
   meters Campaigns, Ads, Edit credits, and Hours only when `included.hours > 0`; head "1 of 3"; fill = used / included
   (capped at 100%); a quiet `meter__note` "2 left this month" when 0 < remaining ≤ 2, "over by 1" when used > included.
   Footer "Starter Pack · renews 15 Nov · next payment 5,000 EGP" (`period_end`, `next_payment`; each part only when
   known). No package: the empty state "No package yet" / "Add one in Settings › Package and usage shows here."
D. **Running jobs** · link `Work` → `/jobs?brand=`. One group per project from `projects` (General first, then `order`):
   open projects (status not done) show their non-archived jobs as rows: title, sub "Posts · 8 items" (type label ·
   `counts.files` items), chip = the job's word from `overview.words` with its suffix (`· 3 items` for pending_review,
   `· 7 Nov` for scheduled / posted, none otherwise). Group head "General `3 of 6`" when the project has more jobs than
   rows (`counts.jobs`), else "Winter campaign `4`". A project with status done folds into one line
   "Branch opening · closed · 1 job" that expands on click (a `ds` disclosure, 44px on the phone). No jobs at all: one
   muted line "No jobs yet." Plans (`type === "plan"`) are not rows here (they live on the Plan tab).
E. **Client feedback and activity** · link `Review queue` → `/review?brand=`. For each open `feedback` item a `.quote`:
   chip `Changes requested`, "Winter catalog v2 · Mona Adel · 1 Nov", then the note in quotes (a link to the item in its
   job). Then two `.act` lines from `overview.activity`: "Mona Adel signed in — Today 09:40", "Mona Adel viewed Winter
   catalog v2 — Yesterday" (relative day words: Today / Yesterday / the date; time only for today). Nothing open and no
   activity: one muted line "No client feedback yet."

Status chip words (EN / AR): Changes requested / مطلوب تعديل · Waiting on client / مستني العميل · Pending review /
في المراجعة · Scheduled / متجدول · Posted / اتنشر · Approved / اتوافق عليه · Delivered / اتسلّم · Planned / مخطط ·
In progress / شغالين عليه · On hold / متوقف · Due / مستحقة · Overdue / متأخرة. Only Approved is green; done states use
cyan / royal tints; `chip--changes` warm; `chip--waiting-client` and `chip--pending-team` neutral-tinted, as `shared.css`
draws them. Day words: EN `plural(n, "day", "days")`, AR يوم واحد / يومين / n أيام (3–10) / n يوم (11+).
