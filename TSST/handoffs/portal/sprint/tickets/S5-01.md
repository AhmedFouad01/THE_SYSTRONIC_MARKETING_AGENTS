## 1. What is true today
- Nothing stores a number: no table holds a goal target or a monthly result (checked `migrations/001`-`037`; the plan says the same, `sprint0-final.json` line 18).
- **The five stages already are `projects.goal`.** The plan's pointer `016_r9.sql:32` shows the OLD labels (`awareness, acquisition, activation, conversion`). `017_r93.sql:4-10` dropped that CHECK, mapped `awareness` to `acquisition` and `conversion` to `revenue`, and set the CHECK to `acquisition, activation, revenue, retention, referral`. `021_r98.sql:4-9` added `stage_extras text[]` (up to 4 more stages, never the primary). Code: `FUNNEL_STAGES` (`src/service/dash/types.ts:205`); a campaign's stages are `[goal, ...stage_extras]` (`projects.ts:60-61`, `goals: FunnelStage[]` at `types.ts:225`). So **the reconcile needs no data change**. The column name `goal` means "primary stage", not a target.
- Naming trap: in code `goals` already means a campaign's list of STAGES (`projects.ts:44`, `types.ts:225`). A new table called `goals` would be read as that. This ticket names the table `campaign_goals` (a deliberate change from the plan's `goals`; Q3).
- Only a campaign can carry them: the CHECK at `016_r9.sql:39-42` allows `goal` only for `type = 'campaign'`; a general or ongoing project has none (`projects.ts:134`, `:354`, `:386`).
- `deleteProject` refuses the General project and a project with jobs, then runs `DELETE FROM portal.projects` (`projects.ts:492-516`). A cascading FK would silently drop results with it: see 2.4.
- The client switch exists: `client_settings.show_growth_report boolean NOT NULL DEFAULT false` (`035_client_settings.sql:28`, `client-settings.ts:12-30`), saved by the one settings route and labelled in the copy (`web/src/copy.ts:999`). Nothing reads it yet. S5-03 does.
- How the repo does "down": there is no down file. Each migration states its manual rollback in the file header and its test applies the file on an empty and a seeded database (`035_client_settings.sql:11` "Rollback by hand: DROP TABLE portal.client_settings"; `037_week_setting.sql:10-14` lists the statements in order, including the runner's own record). The runner (`src/db/migrate.ts:17-20`) runs each file as one implicit transaction with its bookkeeping row and refuses an applied file whose checksum changed; files never contain BEGIN / COMMIT. The deploy script runs migrations while the OLD code serves (S4-00 ticket 1.9).
- Highest migration is `037_week_setting.sql` (S4-07). The next free number is **038**; the builder re-checks at branch time.

## 2. Design
### 2.1 The catalogue (one typed list, no free text)
`src/service/dash/growth-metrics.ts` exports ONE `as const` list and its derived types. Every other place (routes, web, tests, DB checks) reads it or is tested against it.
| id | stage | unit | EN word | AR word (client) |
|---|---|---|---|---|
| `reach` | acquisition | count | Reach | الوصول |
| `visits` | activation | count | Showroom visits | زيارات المعرض |
| `leads` | activation | count | Leads | العملاء المحتملين |
| `orders` | revenue | count | Orders | الطلبات |
Default list = decision 10 without the optional retention and referral metrics (Q2). `Not measured` is the state of a stage with no catalogue metric. The words live in the copy files, not in this list (the list holds ids only; the client words in the client dictionary, the team words in `copy.ts`). `unit` is `count` for all four; the column exists as the plan names it.
### 2.2 Migration `038_goals_results.sql` (additive; forward only; two new tables)
`SET LOCAL lock_timeout = '5s';` first, as 035 and 037.
| Table | Columns | Rules |
|---|---|---|
| `portal.campaign_goals` | `project_id bigint PRIMARY KEY REFERENCES portal.projects (id) ON DELETE CASCADE`, `stage text`, `metric text`, `unit text NOT NULL DEFAULT 'count'`, `target bigint`, `due_at date`, `updated_at timestamptz NOT NULL DEFAULT now()`, `updated_by text NOT NULL DEFAULT ''` | One goal per campaign (the plan: "one goal (metric, target, date)"). CHECK stage in the five; CHECK `(stage, metric)` in the four catalogue pairs; `unit = 'count'`; `target BETWEEN 1 AND 1000000000000`. All of stage, metric, target, due_at NOT NULL |
| `portal.result_entries` | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `project_id bigint NOT NULL REFERENCES portal.projects (id) ON DELETE CASCADE`, `stage`, `month date`, `metric`, `value bigint`, `source text NOT NULL DEFAULT 'team'`, `reported_by text NOT NULL DEFAULT ''`, `reported_at timestamptz NOT NULL DEFAULT now()` | `UNIQUE (project_id, stage, month, metric)`: one value per field. CHECK `source = 'team'` (the only source in S5; a later source widens the CHECK); same stage / pair CHECKs; `month = date_trunc('month', month)::date` (first day); `value BETWEEN 0 AND 1000000000000`. A zero is a real value; "not reported" is no row. Index: the unique index serves `WHERE project_id = $1`; add `(project_id, month)` only if the rehearsal plan shows a need |
`reported_by` holds the team member's name, like `client_settings.updated_by` (`client-settings.ts:55`, written from `c.user.name`, `clients.ts:410`). It is team-only and never in a client read.
### 2.3 Safe on a live Postgres 16
No `UPDATE`, no backfill, no row inserted, no existing table altered. The only lock on an existing table is the share lock `ADD FOREIGN KEY` takes on `portal.projects` (reads continue, writes wait): the table is small and the 5 s `lock_timeout` makes the migration fail clean (nothing left, run again) rather than queue. Idempotence is the runner's record (re-running the runner is a no-op); the file itself uses plain `CREATE TABLE`, as 035. Old-code compatibility: the old release never touches the new tables; its project delete cascades them away, so it cannot break on them. Rollback in the file header, in order: `DROP TABLE portal.result_entries; DROP TABLE portal.campaign_goals; DELETE FROM portal.schema_migrations WHERE name = '038_goals_results.sql';` (a rollback after results were typed loses them: the header says so, and says to dump the two tables first).
### 2.4 Functions (`src/service/dash/growth.ts`, new; the ONLY code that writes the two tables)
- Reads: `goalOf(db, projectId)`, `resultsOf(db, projectId, {from?, to?})`, `goalsOfBrand(db, brand)`, `resultsOfBrand(db, brand, {from, to})` (campaign rows of the brand with the project's name, stage list and `client_visible`; no client filtering here: the client readers of S5-03 filter).
- Writes, per field: `saveGoal(db, projectId, {stage, metric, target, due_at}, actor)` (upsert), `clearGoal`, `saveResult(db, projectId, {stage, month, metric, value}, actor, today)` (upsert on the unique key, last write wins; sets `reported_by`, `reported_at`), `clearResult`. Errors by `invalid` / `notFound` / `conflict` from `server/v1/core.js`, as `projects.ts`.
- Rules checked in code: the project exists and is a campaign, not General (422 / 404); `stage` is one of the campaign's own stages (`[goal, ...stage_extras]`); `(stage, metric)` is in the catalogue; `month` is `YYYY-MM` or `YYYY-MM-01` and not after the current month in Cairo (`dates.ts` / `time.ts` helpers; Q4); integers only; `due_at` is a date not before the campaign's `start`.
- Changed in `projects.ts`: `deleteProject` also refuses with `conflict("cannot delete a campaign that has results")` when `result_entries` holds a row for it (a goal alone goes with the campaign). Changing a campaign's stages never deletes a stored row; a row of a stage the campaign no longer has is kept and still returned (the editor of S5-02 shows it as read-only).

## 4. Acceptance (builder and reviewer check each)
1. 038 applies on an empty database and on a seeded one (`next` data with campaigns, jobs, `client_settings`); a second `migrate` run applies nothing; every existing table's row count is unchanged (`migrate-038: applies, is a no-op the second time, changes no count`).
2. The rollback block in the header, run as written, leaves the 037 schema and the runner can apply 038 again (`migrate-038: the header rollback restores 037 and 038 re-applies`).
3. The DB refuses: a stage outside the five, a pair outside the catalogue, a non-first-of-month `month`, a negative value, a target of 0, a second row for the same (campaign, stage, month, metric), `source <> 'team'`, a project id that does not exist (`migrate-038: each CHECK and key refuses`).
4. Every catalogue row is accepted by the DB and a metric not in the list is refused by the DB: the list and the CHECKs cannot drift (`growth-metrics: the list equals the DB pairs`).
5. `growth-metrics.ts` is the only list: a test fails if a second literal list of the metric ids exists in `src` or `web/src` outside the dictionaries (`growth-metrics: one list`).
6. Deleting a campaign with a goal only works and removes the goal; with a result it answers 409 and removes nothing (`growth: deleteProject keeps a campaign that has results`). Deleting a project through the old SQL path cascades both tables (`migrate-038: cascade`).
7. Writes: a goal saves, edits and clears; a result saves, edits (same key, one row) and clears; zero is stored; two writes of different fields never touch each other; `reported_by` and `reported_at` follow the last write; General, ongoing, unknown project, a stage the campaign lacks, a future month, a non-integer, an unlisted metric are each refused with the right status and write nothing (one test each, named `growth: <rule>`).
8. Reads: `resultsOfBrand` returns only the brand's campaigns, months inside the range, in month order; a stage dropped from a campaign still returns its stored rows (`growth: reads`).
9. No route, no web file, no client payload changes: `tests/client-payload-walk.test.ts` is untouched and green; the docs route table is unchanged (`scripts/route-table.ts --write` shows no diff).
10. Checks green: root typecheck, lint, the full suite with `--no-file-parallelism`; the migration run once on a real local Postgres 16 (throwaway cluster, no real data, deleted after), as S4-00 did, with the result written in the build record.

## 7. Owner questions (defaults let the build proceed)
1. Decision 9, who records a result: any team member, name kept (default; the BOARD recommendation). The functions take an actor name and do not check a role; S5-02 decides the route's access.
2. Decision 10, metrics for v1: reach, visits, leads, orders; retention and referral have none and read "Not measured" (default). Adding `repeat_orders` and `referrals` later is a CHECK widening plus one catalogue line.
3. Table name `campaign_goals` instead of the plan's `goals` (default: yes, to avoid the clash with the stage list called `goals`).
4. Can a team member type a month that has not started (default: no; current and past months only)?
5. One goal per campaign (default, the plan's wording) or one per stage? Per stage would change the key to `(project_id, stage)`; cheap now, a migration later.
