# S2-02: a stable id for every job (`jobs.id` uuid)

Part S2 (foundation). Gate: migration (runs on a local database only until a deploy gate; Ahmed's OK, a fresh
backup and the restore drill S1-02 come before it runs on production). Depends on: S2-01. Size L.
State lives on `../BOARD.md`. **Status: study started 2026-11-06, no code yet.**

## Plan wording
Migration: `jobs.id` uuid + backfill; milestones, item sets, request links FK to it; slug kept for display; endpoints
accept id. Acceptance: renaming a job keeps milestones and links; old links by slug still resolve for one release.
The product pages of the plan use `/jobs/view?id=<uuid>`.

## What the code does today (read at `next` = `d116691`)
- A job has no id. It is the pair `(brand, job)` of two texts, everywhere.
- `job` is one of: a Drive folder path under `projects/` (classic job); `@<slug of the title>` for a job the Dash
  linked to a client folder (`job_sources`, slug fixed at creation, `-2` / `-3` on a clash); a Dash-only job.
- The comments in the migrations say it on purpose: "no foreign key: it outlives a renamed or removed job folder".
  So a renamed Drive folder is a new job, and every row under the old name is orphaned.
- Tables that name a job by text (16 found in `migrations/`): `jobs` (the indexer, key brand+job), `decision_history`,
  `job_meta` (key brand+job), `milestones`, `client_items` (key brand+job+key), `job_sources` (key brand+job),
  `posts`, `plan_imports` (`jobs[]`), `time_entries`, `job_projects` (key brand+job, the row `lockModelJob` locks and
  the only foreign-key target today), `client_activity`, `job_requests`, `items` (unique brand+job+key),
  `job_release_events`, `job_files` (unique brand+job+path), `request_jobs` (FK to `job_projects`).
  Still to check: client links (`jobs` text array), documents, payments, anything in `settings` JSON.
- The API addresses a job as `?brand=&job=` on every route (`docs/DASH-API.md` line 10).
- `job_projects` is in practice the register of the jobs the Dash knows: the one-time "adoption" wrote a row for
  every scanned job, and every create path writes one (`team-write.ts`, `job-sources.ts`). It is the natural owner
  of the id.
- The indexer's table is already called `jobs` and is still used (`src/db/repo.ts` upsert, `team-write.ts` writes
  `package_id` there, `packages.ts` joins it), so "jobs.id" needs a decision: give that table the id, or keep it as
  the index and put the id on `job_projects`.

- Three kinds of job in `jobLoc` (`src/service/dash/jobs.ts`): a classic job is the folder `projects/<job>`; an `@slug`
  job is `job_sources.folder` inside the brand's folder; a Dash job (`job_sources.kind = 'dash'`) lives in the Dash
  media root under its slug (the folder is created on first use).
- For `@slug` and Dash jobs a rename is already only a title change (`job_meta.title`); the slug never changes. The
  real loss is a classic Drive folder renamed outside the Dash.
- The indexer's `jobs` table also carries `package_id` (migration 025).
- Append-only tables (`decision_history`, `item_*`, `job_release_events`) refuse UPDATE by trigger, so a backfill of a
  new column there needs the trigger switched off inside the migration, or those tables keep the text as history.

- Size of the change in code: about 21 places in `src/server` read `?job=`, one central loader (`job()` in
  `src/server/v1/items.ts`), and the web builds a job link in 18 files. `lockModelJob` locks the `job_projects` row.
- The live database was wiped on 2026-10-31 (only new-model data since then), and new work enters by Drive import as
  `@slug` jobs. So the live data is mostly `@slug` jobs, which lowers the backfill risk. To confirm on the restore
  drill copy (S1-02), not by guessing.

## First thoughts, not decided
- Put the id on the register (`job_projects.id uuid`), give the working tables a `job_id` that points to it
  (milestones, items, job_files, posts, request_jobs, time_entries, job_meta), and keep `(brand, job)` text next to
  it for one release so every old query still works while the code moves over.
- A rename then touches one row. For a Drive folder renamed outside the Dash the owner needs one action,
  "this folder is that job" (R60: a new control, so Ahmed is asked first).

## Before any code (next step)
1. A written design, checked by an independent reviewer, that answers:
   - which table owns the id (a new `jobs` identity table, or `job_projects`, or `job_meta`), and what happens to the
     indexer's `jobs` table that already has that name;
   - what "rename" means for each kind of job (a Drive folder renamed outside the Dash cannot be seen as a rename
     without help: how is the link kept, by the folder's own id file, by `job_sources`, or by an owner action
     "this folder is that job"?);
   - which tables get the foreign key now (the plan names milestones, items and request links) and which keep the
     text for history (`decision_history` is append-only);
   - the backfill, and how it is proved on a copy of real data (the restore drill S1-02 gives that copy);
   - the API: `id` accepted next to `brand` + `job`, the old form kept for one release, what the web sends;
   - how it is rolled back.
2. Then small pull requests in order: migration + backfill (local database only) → server reads by id → endpoints
   accept id → web links by id → tests for rename.
