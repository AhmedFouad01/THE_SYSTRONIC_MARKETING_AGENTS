# S2-02: a stable id for every job

Part S2 (foundation). Gate: migration (built and tested on a local database only; Ahmed's OK, a fresh backup and the
restore drill S1-02 come before it runs on production). Depends on: S2-01 (merged). Size L.
State lives on `../BOARD.md`. **Status: design written 2026-11-06, under independent design review, no code merged.**

## Plan wording
Migration: `jobs.id` uuid + backfill; milestones, item sets, request links FK to it; slug kept for display; endpoints
accept id. Acceptance: renaming a job keeps milestones and links; old links by slug still resolve for one release.
The product pages of the plan use `/jobs/view?id=<uuid>`.

## What the code does today (read at `next` = `5e45149`)
1. A job has no id. It is the pair `(brand, job)` of two texts, in every table, every route and every link.
2. `job` is one of three things (`jobLoc` in `src/service/dash/jobs.ts`):
   - a classic job: the folder `projects/<job>` of the client's tree;
   - an `@slug` job: a folder the Dash linked (`job_sources.folder`), slug made from the first title, never changed;
   - a Dash job (`job_sources.kind = 'dash'`): lives in the Dash media root under its slug.
3. **The register already exists: `job_projects`** (key `brand, job`). `scanAll` lists exactly its rows, `scanJob`
   answers 404 for a job that is not in it, every create path writes a row, and `lockModelJob` locks that row.
4. No code changes a job's key or its linked folder. "Rename" today is a title change (`job_meta.title`); it already
   keeps everything. What does break is outside the Dash: a Drive folder renamed by hand. A classic job then becomes
   an unknown folder, and an `@slug` job loses its folder and drops out of the lists (`scanAll` skips a 404).
5. Tables that name a job by text:
   - working tables: `job_meta` (key), `job_sources` (key), `milestones` (job scope), `items`, `job_files`, `posts`,
     `time_entries`, `job_requests` + `request_jobs` (the only foreign key to the register today), `client_items`
     (old model), `jobs` (the first indexer's table, still read for `package_id`);
   - history, append-only by trigger: `decision_history`, `job_release_events`, `client_activity`;
   - lists inside a column: `client_links.jobs`, `plan_imports.jobs`.
6. Nothing ties those rows to the register, so a row can name a job that does not exist. Example: `POST /time`
   checks the folder (`jobLoc`), not the register.
7. In code: 18 places in `src/server/v1` read `?job=`; the web reads `brand` + `job` from the URL on two pages
   (`Job.tsx`, `PostNew.tsx`) and builds job links through `jobHref()` in 15 files.
8. The live database was wiped on 2026-10-31 and new work enters as `@slug` jobs, so live data should be small and
   regular. To be confirmed on the restore-drill copy (S1-02), not assumed.

## Design

### D1. The id lives on the register
`job_projects.id uuid NOT NULL DEFAULT gen_random_uuid()`, unique. Existing rows get their id from the default.
The table keeps its name in this ticket (renaming it to `jobs` collides with the old indexer table; S2-07 cleans names).

### D2. Working tables are tied to the register by foreign key, on the key they already hold
`(brand, job) → job_projects (brand, job)`, with `ON UPDATE CASCADE`, `DEFERRABLE INITIALLY DEFERRED`, created
`NOT VALID`.
- Tables: `job_meta`, `job_sources`, `milestones`, `items`, `job_files`, `posts`, `time_entries`; `request_jobs`
  keeps its key and gains `ON UPDATE CASCADE`.
- Why not a new `job_id` column on every table (the plan's literal wording): it would make two identifiers for one
  fact in seven tables, written twice by every insert, with nothing in the database keeping them equal, in a sprint
  whose goal is one write path per fact. The foreign key on the existing key gives the same guarantees now (no row
  for an unknown job; a changed key follows through) with no change to any insert. The uuid stays the public,
  stable name. If the text key is ever dropped from a table, that table switches to `job_id` then, one at a time.
- `ON UPDATE CASCADE`: a change of a job's key in the register carries to every working table in one statement.
  That is what makes a future "this folder is that job" action safe.
- `DEFERRABLE INITIALLY DEFERRED`: some create paths write `job_sources` and `job_meta` before the register row
  inside one transaction; the check runs at commit.
- `NOT VALID`: old rows that name an unknown job do not stop the migration; new and changed rows are checked. A
  query lists the old rows; they are looked at on the restore-drill copy and validated in a later migration.
- Not tied: the history tables (they keep the name the job had; their triggers refuse updates), the two list
  columns, `client_items` and the indexer's `jobs` (both go away with the old model, S2-03 / S2-07).

### D3. The API accepts the id everywhere, in one place
- Every job card and job detail carries `id`.
- Any route that takes `brand` + `job` also takes `job_id=<uuid>` alone. One resolver in the dispatcher turns it into
  `brand` + `job` before the handler runs: unknown id → 404; an id together with a different `brand` / `job` → 422;
  on client routes an id of another client → 404.
- `docs/DASH-API.md`: "a job is addressed by `job_id`, or by `brand` + `job` (kept for one release)".

### D4. The web links by id
- `jobHref()` builds `/jobs/view?id=<uuid>`; the job page and the post page accept `id`, or `brand` + `job` from an
  old link (kept for one release), and an old link is replaced by the id form once the job is loaded.
- The mock API gives every job a fixed id.

### D5. Rename
Stays a title change. No "change the key" control in this ticket.
- Acceptance test 1: rename a job's title → same id, milestones, items, posts, time and request links still there;
  the link by id and the old link both open it.
- Acceptance test 2 (database): changing a job's key in the register carries to every tied table.

### D6. Found, not solved here
A Drive folder renamed by hand makes its job drop out of the lists. Fixing it needs a new owner control ("this
folder is that job"), so it is a decision for Ahmed (R60) and a later ticket. D2 makes that control a one-row change.

## Rollback
The migration only adds a column and constraints. To undo: drop the constraints and the column (written in the PR).
Code from before this ticket runs on the migrated schema unchanged, because no column it uses changes.

## Risks
- A create path that writes a tied table in its own transaction before the register row would fail at commit:
  every insert site is listed and tested in S2-02a.
- Live rows that name unknown jobs: `NOT VALID` plus the report; nothing is deleted.
- The wipe scripts and tests delete rows in an order that the new keys may refuse: run and fixed in S2-02a.
- A request that names a real folder which is not a registered job now gets a clean 404 instead of writing a row.
