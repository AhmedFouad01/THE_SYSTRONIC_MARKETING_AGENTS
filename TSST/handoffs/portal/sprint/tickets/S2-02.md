# S2-02: a stable id for every job

Part S2 (foundation). Gate: migration (built and tested on a local database only; Ahmed's OK, a fresh backup and the
restore drill S1-02 come before it runs on production). Depends on: S2-01 (merged). Size L.
State lives on `../BOARD.md`. **Status: design v2 (after an independent design review, 2026-11-06); building in five
pull requests; the record of each step is under "Build record" at the end.**

## Plan wording
Migration: `jobs.id` uuid + backfill; milestones, item sets, request links FK to it; slug kept for display; endpoints
accept id. Acceptance: renaming a job keeps milestones and links; old links by slug still resolve for one release.
The product pages of the plan use `/jobs/view?id=<uuid>`.

## What the code does today (read at `next` = `28806f7`, checked by the design reviewer)
1. A job has no id. It is the pair `(brand, job)` of two texts, in every table, every route and every link.
2. `job` is one of three things (`jobLoc` in `src/service/dash/jobs.ts`):
   - a classic job: the folder `projects/<job>` of the client's tree;
   - an `@slug` job: a folder the Dash linked (`job_sources.folder`), slug made from the first title, never changed;
   - a Dash job (`job_sources.kind = 'dash'`): lives in the Dash media root under its slug.
3. **The register is `job_projects`** (key `brand, job`) for the Dash API: `scanAll` lists its rows (minus deleted jobs
   and clients), `scanJob` answers 404 for a job that is not in it, every create path writes a row, `lockModelJob`
   locks that row. Not everything goes through it: Drive folders were registered once (`adoptDrive`), so a classic
   folder made later is not registered; the old board and file routes (`/api/job`, `/api/text`, `/file`, `/thumb`) serve
   any classic folder; client links name their jobs in `client_links.jobs`.
4. **No code changes a job's key or its linked folder.** "Rename" is a title change (`job_meta.title`) and it already
   keeps everything. So the plan's acceptance "renaming a job keeps milestones and links" was already true before
   this ticket. What does break is outside the Dash: a Drive folder renamed by hand.
5. Tables that name a job by text:
   - working tables: `job_meta` (key), `job_sources` (key), `milestones` (job scope; brand and job may be empty),
     `items`, `job_files`, `posts`, `time_entries` (job may be empty), `job_requests.job` (may be empty) +
     `request_jobs` (the only foreign key to the register today), `client_items` (old model), `jobs` (the first
     indexer's table, still read for `package_id`);
   - history: `decision_history` and its view `decisions` (read by brand + job + key in `loadWorld`, `repo.ts`,
     `packages.ts`), `job_release_events` (both append-only by trigger), `client_activity`, and the copy of the post
     row inside `item_versions.preview`;
   - lists inside a column: `client_links.jobs`, `plan_imports.jobs`.
6. Nothing ties those rows to the register, so a row can name a job that does not exist. These handlers write after
   checking only that the folder exists: `PATCH /job/meta`, `POST /job/archive`, `POST /job/restore`,
   `POST /milestones`, `POST /time`.
7. A job is named in the query (`?brand=&job=`) on 18 places of `src/server/v1`, in the JSON body on others
   (`POST /time`, `/milestones`, `/items`, `/decisions`, team `PATCH /requests`, client `POST /decisions`), in the path
   on `PATCH /jobs/:job`; client routes take the brand from the session. The web reads `brand` + `job` from the URL on
   two pages and builds job links through `jobHref()`.
8. The live database was wiped on 2026-10-31 and new work enters as `@slug` jobs, so live data should be small and
   regular. An assumption until measured on a copy of real data.

## What this ticket delivers (said plainly)
- Every job has a stable id that the API returns and that a link can carry.
- A new row can no longer name a job that is not registered.
- Old links by `brand` + `job` keep working.
- It does **not** add a way to change a job's key, and it does not fix a Drive folder renamed by hand (D6).
- "Renaming a job keeps milestones and links" stays true (it was true before); one test pins it.

## Design (v2)

### D1. The id lives on the register
`ALTER TABLE portal.job_projects ADD COLUMN id uuid NOT NULL DEFAULT gen_random_uuid();` and
`ADD CONSTRAINT job_projects_id_key UNIQUE (id)`. Existing rows get one value each from the default (checked on the
embedded database: distinct per row). `gen_random_uuid()` is already used by migration 027.

### D2. Working tables reference the register, on the key they already hold
`FOREIGN KEY (brand, job) REFERENCES job_projects (brand, job) DEFERRABLE INITIALLY DEFERRED NOT VALID`, no cascade.
- Tables: `job_meta`, `job_sources`, `milestones`, `items`, `job_files`, `posts`, `time_entries`.
  `request_jobs` keeps the key it has.
- Why not a `job_id` column on every table: two identifiers for one fact in seven tables, written twice by every
  insert, with nothing keeping them equal. The key they hold never changes, so a reference on it is enough for "no
  row for an unknown job". What it gives up: rows cannot be joined by id alone, and dropping the text key later means
  a migration per table. Accepted for this sprint.
- **No `ON UPDATE CASCADE`** (v1 had it): no feature changes a key, and the history tables, the client links and the
  request rows would not follow, so a cascade would look safe and break approvals and client access. A key cannot
  change while rows hang on it; that is the honest state.
- **Deletes are refused** while rows hang on a job or on a client's jobs (the default action). Jobs and clients are
  hidden, not deleted (R60). A hard delete by hand must remove the rows first.
- `DEFERRABLE INITIALLY DEFERRED`: a create path may write `job_sources` and `job_meta` before the register row in
  one transaction; the check runs at commit.
- `NOT VALID`: rows from before the migration that name an unknown job stay; new and changed rows are checked. A
  query lists the old rows; they are validated in a later migration once the list is empty on real data.
- A row with an empty job (client-level time, a campaign or client milestone) is not checked.
- Not tied: the history tables, the two list columns, `job_requests.job`, `client_items` and the indexer's `jobs`.

### D3. Handlers check the register before they write
The five handlers of fact 6 load the world (which registers Drive folders the first time) and refuse an unregistered
job with `404 unknown job` before any write. Without this the new reference would turn those writes into `500`.
A `23503` on these references is also mapped to 404, as a backstop.

### D4. The API accepts the id
- Every job card and job detail carries `id`.
- `job_id=<uuid>` is accepted in place of `brand` + `job` on every `/api/v1` route that names the job in the query
  string; one resolver in the dispatcher turns it into `brand` + `job` before the handler runs. Team routes: unknown
  id → 404; an id with a different `brand` / `job` → 422.
- Client routes: the id is resolved only inside the client's own brand; anything else behaves exactly like a job the
  link cannot see (the handler's usual 404), never a 422, so an id tells a client nothing.
- Not covered in this ticket, said in the docs: routes that name the job in the body or in the path, and the old
  board and file routes. The web does not need them: it opens a job by id, then uses the `brand` + `job` of that job.
  S2-06 (server split by domain) moves the body routes to the same helper.

### D5. The web links by id
- `jobHref()` builds `/jobs/view?id=<uuid>`; the job page and the post page accept `id`, or `brand` + `job` from an
  old link (kept for one release), and replace an old link by the id form once the job is loaded.
- The job page already uses `?from=project&id=<number>` for "back to the campaign": that becomes `project=<number>`;
  an old link with a number in `id` still works.
- The mock API gives every job a fixed id.

### D6. Found, not solved here
A Drive folder renamed by hand: a classic job becomes an unknown folder, and an `@slug` job loses its folder and
drops out of the lists. For an `@slug` job the fix is to point the job at the new folder (`job_sources.folder`), no
key change. Either way it is a new owner control, so it is a decision for Ahmed (R60) and a later ticket.

- 031: `ALTER TABLE portal.job_projects DROP CONSTRAINT job_projects_id_key, DROP COLUMN id;`
- 032: drop the seven constraints. Code from before S2-02b on the 032 schema would answer 500 on the five handlers,
  so 032 never goes out before S2-02b.
- The migration runner has no down step: these statements are run by hand, after a restore decision.

clean checkout of `next`. Verdict on v1: **sound with changes**. It confirmed D1 and the mechanics of D2 on the
embedded database, and asked for these changes, all taken in v2:
1. one resolver in the dispatcher cannot cover body and path routes → D4 says exactly what is covered;
2. the references would answer 500, not 404, on five handlers → D3, merged before the references;
3. wipe script 002 fails on the new schema → fixed in S2-02c;
4. "a key change carries" was overclaimed (history, client links and requests would not follow) → no cascade;
5. the rename acceptance was met only by definition → said plainly above;
6. the rollback claim was wrong → rewritten;
7. delete behaviour was not stated → stated;
8. a client must never learn that an id exists → D4;
9. split the id from the references → five increments.
Also run locally: with the references applied and no other change, 28 of 610 tests failed, in six files, all for the
reasons above (the five handlers, the wipe script, a hand delete of a client, the pinned migration list).
