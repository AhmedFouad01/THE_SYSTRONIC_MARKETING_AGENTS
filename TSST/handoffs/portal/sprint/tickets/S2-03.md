## Plan wording
Keep the items/versions decision path; `POST /decisions`, `/decisions/batch` (legacy), `/api/decision`,
`PATCH /job/items` return 410; drop the `decision_history` trigger; `loadWorld` side effects moved to explicit POSTs.

### More facts (added 2026-11-06)
- **Why "Change my decision" answers 409** (the evaluation, `~/Work/DASH-SPRINT0/sprint0-all.json`): a read syncs the
  job, the sync creates a new version of the item when a file changed, and the client's change then names an old
  version ("the item has a newer version"). The fix is at the root: reads must not write.
- **`decideItem` today** (`job-model.ts:184-232`): checks the version, the note, the live version (a client may take
  an approval back until the item is scheduled or posted: `approval_locked`), then inserts a `decision_history` row;
  the trigger inserts `item_decisions`, sets `live_version`, resets `withdrawn` / `sent_version` and releases items.
  `releaseItems` (`job-model.ts:150`) already does the trigger's release in TypeScript (it is used by `changeJobModel`).
- **Other writes on a read:** `snapshotFiles` (`item-files.ts:12`) copies files and inserts `item_version_files` when
  the sync makes a version; a client request updates `client_links.last_used_at` / `client_people.last_seen`
  (`client-session.ts:184`, `:244`); `logActivity` inserts into `client_activity` at most once per window.
- **The deploy script** (`scripts/deploy.sh:135-141`) runs the migrations while the OLD code is still serving, then
  switches and restarts; `--rollback` puts the old code back on the migrated schema. So a migration must work with
  the code before it, and nothing the old code needs may be dropped in the same release.
- **Measured (a scratch run):** with the sync switched off inside reads and nothing else changed, 19 of 670 tests fail
  in 11 files. The ones looked at are all "a write, or a later read, expected rows that a read used to create"
  (a file to share, the file count on a card, a client's deliverables).
- **Tests on the old routes:** 22 test files call them 94 times (`/decisions` 46, `/job/items` 26,
  `/client-view/decisions` 10, `/api/decision` 10, `/decisions/batch` 2), mostly as setup for other tests.

## What this ticket delivers (said plainly)
- One code path writes a decision, `decideItem`, and it no longer needs a database trigger to finish the job.
- The five old decision routes answer 410. The old board at `/legacy` loses its decision buttons and stays to read.
- A read never changes job data: the sync with Drive runs at server start, on a timer, when the team asks for it and
  inside the writes that need it.
- The sync makes a new version of an item only when a file's bytes changed, not when only its time changed. This is
  what ends the 409 on "Change my decision" for the user, not only in a test.
- It does **not** move the readers of `decision_history` to the item tables, it does not delete the old tables, and
  it does not drop the trigger yet (S2-07, with the import tool).

## Design (v2)

### D1. `decideItem` does the work; the trigger steps aside row by row
- Migration `033`:
  - `ALTER TABLE portal.decision_history ADD COLUMN bridged boolean` (no default; the view `portal.decisions` names
    its columns, so it does not change);
  - `CREATE OR REPLACE FUNCTION portal.bridge_item_decision()` with the whole body as it is installed after 032 (the
    `FOR NO KEY UPDATE` line included) plus one first statement: `IF NEW.bridged THEN RETURN NEW; END IF;`.
    The whole body is in the file, so the repository shows the real function.
- `decideItem`, after its checks and in this order, in its transaction:
  1. inserts the `decision_history` row with `bridged = true` (the trigger returns at once for it);
  2. inserts the `item_decisions` row;
  3. a client approval after a team approval of that version sets `live_version`;
  4. a team decision clears `withdrawn`, and sets `sent_version` to NULL unless it is an approval;
  5. a team approval calls `releaseItems` (it reads the rows written above and honours `hold_until_all`).
- No session state: a row without the mark (the release before this one, the import tool, `resetApprovalIfNeeded`)
  still goes through the trigger exactly as today. New code on a database without 033 fails loudly on the unknown
  column, so a decision is never written twice or lost in any order of deploy or rollback.
- The note `Edited after review` (the trigger skips it) becomes one constant used by its writer.
- `decideItem` keeps writing one `decision_history` row per decision, so every reader of the old table stays as it is.
  Named costs: that table has no version, and a "Change my decision" still counts as an edit there (as today).
- Tests: the same sequences run through the old path (a row without the mark, the trigger acts) and through
  `decideItem`, then `item_decisions`, `items` and `item_events` are compared. The matrix: team and client; approve,
  changes requested, pending; hold on with a withdrawn item and a hidden item; a decision on the live version and
  "Change my decision"; the `Edited after review` note; the import tool and `resetApprovalIfNeeded` still bridged.
- Dropping the trigger (S2-07) needs the import tool moved to the item path first, or a decision that imports no
  longer reach items. Written here so it is not forgotten.

### D2. The old routes answer 410
- `POST /api/v1/decisions`, `POST /api/v1/decisions/batch`, `PATCH /api/v1/job/items`,
  `POST /api/v1/client-view/decisions` and `POST /api/decision` answer `410` with `{ code: "gone", message }`; the
  message names `POST /api/v1/items/:id/decisions`. Authentication still comes first (no session: 401).
  The client route is in the list because it was the last writer outside `decideItem` (no lock rules).
- The old board (`public/board.html`) posts to `/api/decision`: its decision buttons are removed and one line says
  where decisions are made now. The board still reads.
- `PATCH /job/items` was the only writer of `client_items` ("show to the client", the client's title and caption,
  the maker). Before closing it, increment c confirms from the code which flag a client's view really uses for a
  file (`client_items.shown` or `job_files.shared_with_client`) and says so in its pull request. The "maker" mark
  (human or AI, used for time estimates) has no screen that sets it today; after this it has no route either.
- Web: the four API client functions go, with the components that nothing renders (`ds/PostGrid` after its users are
  traced, `review/Deliverables` and `pages/client/ClientDeliverables`, `review/BulkReview` and `lib/bulk-review`,
  `ClientItemEditor`), the decision branch of `ds/PostsList` (it cannot run in the team mode that renders it) and
  their mock handlers.
- Tests: each of the 94 calls is a test of the old route (it becomes a 410 test), setup for another test (it moves
  to the item route or to `PATCH /job/files`), or a test of behaviour that has no writer left (it goes, listed).

### D3. A read never writes job data
- `detailOf` loses its sync transaction. What it still does is read: the items, the job's file rows, and the marks
  it copies onto posts when an item exists. So a new Drive post has no item until the next sync; the job page shows
  it once the sync it asks for has run.
- `loadWorld` loses `adoptDrive` and its loop over every job (the loop existed only to sync; `world.items` is loaded
  from the items table already).
- `syncJob(env, world, sj)` is today's transaction, with one change: **a new version only when the bytes changed.**
  Today the fingerprint is path + size + time, so a file touched on Drive makes version 2 and outdates the client's
  open review. The sync keeps the quick check (path, size, time: equal means nothing to do) and, when that differs,
  compares the file's bytes with the copy kept for the current version (`item_version_files`); equal bytes only
  refresh the stored fingerprint.
- When the sync runs:
  1. at server start and on a timer in `src/server/main.ts` (every 5 minutes, never two at once), outside any request;
  2. `POST /api/v1/sync` (team): one job (`brand` + `job`, or `job_id`) or all; it answers `{ jobs, changed }`. The
     web calls it when the team opens the jobs list, a job page or the review page, and reloads when `changed > 0`;
  3. inside the writes that need the job's rows. The list, each checked when it is built: the item routes that go
     through `job()` in `items.ts` (non-GET), `PATCH /job/files`, `POST /time` with a key, the post routes
     (`posts.ts`: create from a Drive folder, update, delete; the Dash-made posts already sync themselves). Reads
     (packages, time summary, marketing, client views) never sync.
- `adoptDrive`: `main.ts` already runs it at start; `POST /sync` and `requireRegisteredJob` call it; the test harness
  calls it after it builds its folders (the tests do not go through `main.ts`).
- A client session never syncs. Until the next sync a client keeps seeing an item whose Drive post was removed.
- Still allowed on a read: for a client, `client_links.last_used_at`, `client_people.last_seen`, `client_sessions`
  and the `client_activity` log (`GET /c/<token>`, `/file`, `client-view/job`, the project view); for the team, the
  sign-in session refresh of the auth layer (once a day); on disk, the thumbnail cache.
- Test "reads perform no writes": the guard is armed in the test harness for **every GET of the whole suite** (so a
  GET added later is covered): a team GET runs with the database refusing writes (`default_transaction_read_only`),
  a client GET runs behind a wrapper that lets through only the four client tables above. The older non-v1 routes
  (`/api/tree`, `/file`, `/thumb`, `/c/<token>`) get their own small test.
- Tests "Change my decision", three variants: (1) the client approves, a file's time changes, pages are read, the
  client changes its decision: 200; (2) the same with a team sync in between: still version 1, 200; (3) the file's
  bytes change and the team syncs: version 2, and the client's change on version 1 answers the "newer version" 409.

### D4. Not solved here
- `decision_history` keeps receiving a row per decision; its readers move to the item tables in a later ticket.
- A browser tab opened before increment b does not call `POST /sync`: until it is reloaded, new Drive posts show
  after the timer's next run, not at once. The team reloads after that deploy.
- The trigger and the function stay until S2-07 (with the import tool).

### D5. Increments (each a pull request into `next`, in this order)
- **S2-03a:** D1 (migration `033`, `decideItem`, the comparison tests).
- **S2-03c:** D2 (the five routes, the board, the web functions, components and mock handlers, the tests moved).
  It comes before b because it is mechanical and removes the last old writers.
- **S2-03b:** D3 (the sync out of reads, the byte check, start-up and timer, `POST /sync`, the web's calls, the
  guard in the harness, the three "Change my decision" tests). Last, because it changes when things appear.

### Deploy notes
- `033` works with the code before it (rows without the mark go through the trigger) and after a rollback.
- After S2-03b a new Drive file shows after the next sync (at most 5 minutes, or at once when the team opens a page).
- The web and the server of S2-03b go out together; the team reloads its tabs.
