## Plan wording
Keep the items/versions decision path; `POST /decisions`, `/decisions/batch` (legacy), `/api/decision`,
`PATCH /job/items` return 410; drop the `decision_history` trigger; `loadWorld` side effects moved to explicit POSTs.
Acceptance: legacy routes return 410 with a message; "Change my decision" no longer 409s in the test; reads perform
no writes (test on a read-only connection).

### More facts (added 2026-11-06)
- **Why "Change my decision" answers 409** (the evaluation, `~/Work/DASH-SPRINT0/sprint0-all.json`): a read syncs the
  job, the sync creates a new version of the item when a file changed, and the client's change then names an old
  version ("the item has a newer version"). The fix is at the root: reads must not write.
- **`decideItem` today** (`job-model.ts:184-232`): checks the version, the note, the live version (a client may take
  an approval back until the item is scheduled or posted: `approval_locked`), then inserts a `decision_history` row;
  the trigger inserts `item_decisions`, sets `live_version`, resets `withdrawn` / `sent_version` and releases items.
  `releaseItems` (`job-model.ts:150`) already does the trigger's release in TypeScript (it is used by `changeJobModel`).
- **Other writes on a read:** `snapshotFiles` (`item-files.ts:12`) copies files and inserts `item_version_files` when
  the sync makes a version; a client request updates `client_links.last_used_at` / `client_people.last_seen`
  (`client-session.ts:184`, `:244`); `logActivity` inserts into `client_activity` at most once per window.
- **The deploy script** (`scripts/deploy.sh:135-141`) runs the migrations while the OLD code is still serving, then
  switches and restarts; `--rollback` puts the old code back on the migrated schema. So a migration must work with
  the code before it, and nothing the old code needs may be dropped in the same release.
- **Measured (a scratch run):** with the sync switched off inside reads and nothing else changed, 19 of 670 tests fail
  in 11 files. The ones looked at are all "a write, or a later read, expected rows that a read used to create"
  (a file to share, the file count on a card, a client's deliverables).
- **Tests on the old routes:** 22 test files call them 94 times (`/decisions` 46, `/job/items` 26,
  `/client-view/decisions` 10, `/api/decision` 10, `/decisions/batch` 2), mostly as setup for other tests.

## What this ticket delivers (said plainly)
- One code path writes a decision, `decideItem`, and it no longer needs a database trigger to finish the job.
- The old decision routes answer 410.
- A read never changes job data. The 409 on "Change my decision" that came from a read is gone.
- It does **not** move the readers of `decision_history` to the item tables, it does not delete the old tables, and
  the old board stays (read only) until S2-07.

## Design (v1)

### D1. `decideItem` does the work; the trigger stands down now and is dropped later
- After its checks, in the same transaction, `decideItem` itself: inserts the `item_decisions` row; on a client
  approval after a team approval sets `live_version`; on a team decision clears `withdrawn` and, unless it is an
  approval, `sent_version`; on a team approval calls `releaseItems` (which honours `hold_until_all`).
- It still inserts one `decision_history` row per decision, exactly as today, so every reader of the old table stays
  as it is (the job's history, edit credits, the feedback list, the first-decision date, the export for the PC).
- The trigger cannot be dropped in the same release (see the deploy script above): the old code needs it during the
  deploy and after a rollback. So it stands down by a flag:
  - migration `033` changes the installed function `portal.bridge_item_decision()` in place (the technique of 032):
    one new first line returns at once when `current_setting('portal.decided_in_app', true) = 'on'`;
  - `decideItem` sets that flag for its transaction (`set_config('portal.decided_in_app', 'on', true)`);
  - code without the flag (the release before, the import CLI) gets the trigger as before.
- Dropping the trigger and the function is one line in S2-07, when no release that needs them can come back.

### D2. The old routes answer 410
- `POST /api/v1/decisions`, `POST /api/v1/decisions/batch`, `PATCH /api/v1/job/items`, `POST /api/decision` (the four
  the plan names) and `POST /api/v1/client-view/decisions` (the old client route, not named in the plan: for the
  reviewer to confirm) answer `410` with `{ code: "gone", message }`, the message naming
  `POST /api/v1/items/:id/decisions`. Authentication still comes first (no session: 401).
- `PATCH /job/items` was also the only writer of `client_items` ("show to the client", the client's title and
  caption, the maker). Those have no writer after this; a file is shared with `PATCH /job/files`, an item by a team
  approval. The readers of `client_items` keep reading the rows that exist.
- Web: the four API client functions go, with the components that nothing renders (`ds/PostGrid`,
  `review/Deliverables` and `pages/client/ClientDeliverables`, `review/BulkReview` and `lib/bulk-review`,
  `ClientItemEditor`) and their mock handlers. `ds/PostsList.tsx:199` (its client branch) is checked first.
- Tests: each of the 94 calls is one of three things: a test of the old route (it becomes a 410 test), setup for
  another test (it moves to the item route or to `PATCH /job/files`), or a test of behaviour that has no writer left
  (it goes, listed in the pull request).

### D3. A read never writes job data
- `detailOf` loses its sync transaction; `loadWorld` loses `adoptDrive` and its loop over every job.
- `syncJob(env, world, sj)` is that transaction, unchanged (posts become items, `job_files` rows, items of a post that
  is gone are hidden). It is called by:
  - the write handlers that need the job's rows (one helper for every non-GET handler that reads the job's detail);
  - `POST /api/v1/sync` (team): one job (`brand` + `job`, or `job_id`) or all jobs; it answers `{ jobs, changed }`.
    The web calls it when the team opens a job page (that job) and the jobs list or the review page (all), and
    reloads what it shows when `changed > 0`.
- `adoptDrive` runs at server start and inside `POST /sync`; `requireRegisteredJob` (S2-02b) keeps calling it.
- A client session never syncs.
- Still allowed on a read: the session upkeep (`client_links.last_used_at`, `client_people.last_seen`, the sign-in
  session) and the client activity log.
- Test "reads perform no writes": a database wrapper that, while a GET is served, throws on any INSERT, UPDATE or
  DELETE outside that short list. It calls every GET route of the dispatcher's route table, as the team and as a
  client, so a GET route added later is covered without editing the test.
- Test "Change my decision": a client approves; a file of the post changes on the disk; the client and the team open
  pages; the client changes its decision and gets 200. On today's code the read makes version 2 and the answer is 409.

### D4. Not solved here
- `decision_history` keeps receiving a row per decision; its readers move to the item tables in a later ticket.
- A sync still makes a new version when a file's size or time changes, so an explicit team sync can still outdate a
  client's open review. Only reads stop doing it.
- New Drive posts become items when a team member opens the Dash or writes to the job, not on a client's visit.

### D5. Increments (each a pull request into `next`, in this order)
- **S2-03a:** `decideItem` does the work; migration `033` (the trigger stands down by the flag); tests that the result
  is the same as with the trigger over the cases (team / client, approve / changes, hold, withdrawn, live version).
- **S2-03b:** reads do not write: `syncJob`, `POST /sync`, adoption at start, the web's calls, the two tests of D3.
- **S2-03c:** the old routes answer 410; the web functions, the unrendered components and the mock handlers go; the
  tests move or go.

### Deploy notes
- `033` works with the code before it (no flag, the trigger behaves as today) and after a rollback.
- After S2-03b a new Drive file shows in the Dash after the next sync, not on the next read.

## Questions for the design reviewer

   import CLI, a pooled connection that keeps a setting, a decision made by code that forgets the flag.
3. Which write handlers need `syncJob` (the full list), and is "the web calls `POST /sync`" enough for the jobs list
   and the review page to be fresh?
4. Is the list of writes allowed on a read right, and can the test hold it?
5. Does anything live still call the old routes: a web screen, the PC pull / import task, the old board?
6. Should `POST /client-view/decisions` answer 410 too?
