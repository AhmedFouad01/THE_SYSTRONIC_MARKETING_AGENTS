## 3. The scheduling rule (Decision 19)
**Where a post's life can become `scheduled`** (all of them, proof in 1): (1) `POST /posts` (also the wizard and the sheet: the web's `createPost`, `endpoints.ts:132`, builds it from `postWizard.ts:186`); (2) `PATCH /posts/:id` (the item panel, the row control, the bulk, the post editor). Nothing else: the bulk is N calls of (2); `PATCH /items/:id`, plan, Drive import and sync cannot. A test lists the writers: any new `UPDATE portal.posts ... life` fails the test (`tests/schedule-gate.test.ts`, grep of `src/`).
**The gate = a change TO `scheduled`** (`life === 'scheduled'` and the stored life is not): on `POST` the stored life is "none", on `PATCH` it is `row.life`. A date change on an already scheduled post, or `life` repeated as `scheduled`, is not a change: allowed as today (Reschedule). Un-scheduling (`scheduled` to `draft`) is allowed as today.
**Ads (G5):** the same gate on a change from `draft` / `rejected` to any other ad life (`in_review`, `active`, `paused`, `completed`), because the step table calls those lives `done` (`S4-00.md:165`). Question Q3.

| Client | Rule | Where it runs |
|---|---|---|
| **Without a review order** (every real client) | **Nothing changes.** `loadTurnBase` returns null, so the gate is not asked and the request body, answer, status codes and rows written are as today. A body that carries the new key `schedule_without_approval` is refused 422 `invalid` (the exception has no meaning there). | `schedule.ts` returns before any read |
| **With one** | Allowed only when `turnIn(...).step === 'ready'` (live version = the approver's approval, life `draft`; `scheduleGate`). Else 409 `not_approved`, message "this post is not approved yet; it can be scheduled after the approver's approval". | inside the existing transaction, **after** `lockModelJob` and the freshness check, **before** the UPDATE (`publishing.ts:567-575`); on `POST`, an ordered client always refuses (a new post has no approval), even with the flag |

*Proof of "no change for unordered clients":* (a) the gate's first line is `if (!base) return` where `base = loadTurnBase(...)`; (b) a test runs the same request set (create scheduled, patch to scheduled, repeat, with and without an approval, ad lives) on an unordered client before and after and compares status, body and rows; (c) the existing publishing tests stay green unchanged (`tests/v1-posts*.test.ts`, names not read); (d) the web rule for unordered clients (client-approved = `ready`) equals the old `isClientApproved` UI.

**The exception "Schedule without approval"** is the same `PATCH /posts/:id` with `life: 'scheduled'` plus the body key `schedule_without_approval: true` (no new route: the life change and the record are one transaction under the job lock; the key joins `exact(...)` keys at `publishing.ts:484`). Rules:
- Who: an **active owner** (`c.user.role === 'owner'`) **or the client's named reviewer** (`turn.reviewer.id`, i.e. `base.brand.reviewer_user_id`). Anyone else: 403 `schedule_exception_forbidden`. The maker rule of Decision 18 does not apply (it is a recorded override, not a decision); Q1.
- When: steps `review`, `approval`, `held`, `changes`. Step `planned`: 409 `not_submitted` (send it first). Step `ready`: 409 `exception_not_needed` (an approved post is scheduled normally; a false "without approval" is never recorded; also the race: the approver approved between the confirm and the click). Step `done`: 409 `conflict` as for any no-op (already scheduled or posted).
- Needs `life: 'scheduled'`, else 422 `invalid`. Needs the item (not on `POST`).
- Recorded in the same transaction: one `item_events` row: `action 'schedule_exception'`, `item_id`, `version = current_version`, `by` = the user's name, `by_user_id` = the actor, `at` = now, `note` = **the approver's label at that time** ("Mona Adel", else the client's name) so the line stays true if the approver changes later, `from_user_id`/`to_user_id` NULL. No other free text (the drawn confirm has no note field; S4-00 2.8 said "required note": the drawing wins, Q2).
- What the post becomes: `life = 'scheduled'`, `publish_on` as sent or kept. `live_version` stays null; the turn keeps its real step (e.g. Waiting on client) and is **not** `done`, so the approver can still approve (then `live_version` is set and the step becomes `done`, "Scheduled"). `Mark posted` stays refused (409, `publishing.ts:572`) until it is approved: stated, not changed. **Gap G6:** the row of an exception-scheduled post needs a word that it is scheduled; proposal: the sub-line reads "made by Sara Hassan · Scheduled without approval" («اتجدول من غير موافقة»), chip unchanged. Whether a client request for changes is still possible on a scheduled item: `approvalLocked` (`job-model.ts:211`, `:313`) is used only to refuse taking back an approval; the builder checks the other path and writes the result in the PR.
- **What Activity shows:** `GET /job` (team) gains `schedule_exceptions: [{ item_id, title, version, by, by_user_id, at, approver }]`, read in `teamJobDetail` with ONE query for the job's items; no client payload gains it (walk test). The Activity modal merges them with decisions by `at`: "Ahmed Samir scheduled Post 4 without Mona Adel's approval" + time (SPEC 5, inset d). AR line: **gap G7**, proposal «أحمد سمير جدول بوست 4 من غير موافقة منى عادل» built from the same parts (Ahmed to confirm).
- Errors, all `ApiError(status, code, message)`, all new codes in `copy.scheduleRefusal` EN + AR: 409 `not_approved`; 403 `schedule_exception_forbidden`; 409 `exception_not_needed`; 409 `not_submitted` (existing code); 422 `invalid` (flag with a life other than scheduled, or on an unordered client); existing 409 `conflict` ("the post changed", "newer version") unchanged.

**A scheduled post edited after approval** (`turn.edited_after_approval`): no block and no automatic un-schedule: the approved live version stays the published one (`publishing.ts:561`, "Content edits leave the approved live version ... in place"); the new version is Planned again for an ordered client (S4-00 2.3) and goes through review. Web: the row keeps its chip; the panel shows the existing "newer version" words; **G8: no SPEC word** for "edited after approval"; proposal: nothing new on the row, the flag is returned and tested, a quiet line waits for Ahmed's word. Not changed server-side.

## 4. Each post's own publish date and bulk schedule
- **Data:** already per post (1). No migration, no new field. The row reads `turn.publish_on`. A new `viewer.schedule` on the turn (team payloads only, next to `viewer.decide`): `{ ok: boolean, reason: 'not_approved' | null, exception: boolean }` computed by the SAME function the PATCH uses (`scheduleVerdict(turn, actor)` in `schedule.ts`), so the row's control and the server cannot disagree. Never on a client payload.
- **Control per row:** by step and `viewer` (table in 2). Setting or changing the date is in the Schedule sheet (and the post editor); there is no inline date editor in the drawing.
- **Bulk schedule:** a row is selectable only when it shows Schedule: post item, `turn.step === 'ready'`, life `draft`, a date, not past. The bar "Schedule selected (N)" runs `scheduleItems(targets, patch)` in `web/src/lib/item-bulk.ts`: one `PATCH /posts/:id { version, life: 'scheduled' }` per item, **in sequence**, each with the item's own date (already on the post), progress, a per-item result `{ saved, failed[{ id, title, message }] }` like `approveItems` (`item-bulk.ts:9-26`); a failure never stops the rest. **No batch route:** the gate, the job lock and the freshness check are per post; a batch route would copy them and a second place to keep equal. N is a job's posts (tens). The confirm lists the picked posts with their days. The exception is never bulk.
- The existing bulk **approve** (check on rows that wait for the team, `BulkApprove`): the drawing has checks on approved rows only. Q4.
