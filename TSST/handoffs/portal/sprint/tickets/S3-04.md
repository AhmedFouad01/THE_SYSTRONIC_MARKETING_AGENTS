## Design

### 1. Plan tab (`?tab=plan`)
A. **Title row** "Growth stages" + `New campaign` (primary; owner) → the campaign form (§ 3) as a modal in create mode
   (type campaign). On the phone the button is full width under the title.
B. **Stage board**: five columns in funnel order, each head = numbered stage square in the stage tint + stage name. The
   column of `here.stage` is raised (`is-here`) with the tag "We are here" (only when `here.state` is running or
   between and a campaign exists; no tag for a client with no campaign). Each campaign of the stage is a card: name;
   for an open campaign the Milestones meter "4 of 7" with the dots, "Next: Showroom shoot · 12 Nov" (when one exists),
   "4 running jobs"; for a done campaign "Closed 30 Sep · 7 of 7 milestones"; foot = status chip (Planned / Active /
   Paused as `status-words.css` draws them; done = `chip--ended` "Closed", with "· hidden from client" when
   `client_visible` is false) + `Open campaign` (quiet, sm) → `/clients/project?brand=&id=`. An empty stage reads
   "Nothing planned". A campaign with several goals sits in the column of its first goal. Phone: one column; the
   current stage first as a full card, the other stages as rows (`is-mini`: head + its cards, or "Nothing planned" at
   the end of the row).
C. **Off-stage line** under the board: chip "Not on a stage" + each ongoing project "General · 3 running jobs" + `Open`
   → its project page. Hidden when there is no ongoing project.
D. **Lower grid** (1.4fr / 1fr; one column on the phone):
   - "<campaign> · milestones" for the campaign of `here.project_id` (else the first open campaign; no campaign → the
     brand's client-scope milestones under the title "Milestones"): numbered rows, done = check in the royal tint, the
     next one in the cyan tint with a chip "Next", date at the end ("20 Oct"; weekday for the upcoming ones "Thu 12 Nov").
     Link "Edit on the campaign page" → the campaign page. Read-only here. Empty: "No milestones yet."
   - "Strategy documents": plan-type jobs as rows (`doc` tile "MD", title, sub "Plan job · updated 28 Oct"), `Open` →
     the job; head action `Import plan.md` (quiet, sm; owner) → the existing plan import flow. Empty: "No strategy
     documents yet."
E. Gone from the tab: the action row, `PlanBoard`, `PlanJobs`, `ClientPostsList`, `MilestoneEditor`, `ClientTimeline`,
   the Manage projects modal. Where each function goes: create / edit a campaign → New campaign and the campaign page;
   reorder projects → dropped (the board orders by stage and dates; `POST projects/reorder` stays unused by the web);
   move a job → the campaign page; milestones add / edit / done / delete → the campaign page (project scope) — client-
   and job-scope milestones are added from an `Add milestone` item in the milestones card head menu (⋯) on the Plan tab
   when no campaign is in view, and on the job page as today; Add plan job → `Import plan.md` + the title-row `New job`
   (type plan); Import from Drive → the title-row `New job` modal if it offers Drive, else keep `Import from Drive` as
   a second item in the Strategy documents head menu; upcoming posts → the Work page (`/jobs?brand=`), already linked
   from Overview. List the final placement in the PR body.

### 2. Campaign page (`/clients/project?brand=&id=`, rewrite of `ProjectView.tsx`)
- Back link to the client's Plan tab. Title = the project name; fact strip: stage chip(s) in the stage tint, status
  chip, "12 Oct – 30 Nov" (the dates that exist), "Hidden from client" when `client_visible` is false. Title-row
  action `Edit campaign` (owner, secondary) → the form of § 3 in edit mode.
- "Milestones" card: the project's milestones as numbered rows with a done toggle (`Toggle` or a check `IconButton`
  from the DS; saves `PATCH milestones/:id { done }` on change), title, date; ⋯ per row = Edit (the existing
  `MilestoneModal` in edit mode), Delete (`ConfirmDelete`); head action `Add milestone` (primary, sm) →
  `MilestoneModal` with scope project and this `project_id`. Team members may add / edit (the routes are `team`).
- "Jobs" card: the project's jobs as rows: title (link to the job), sub "Posts · 8 items", the job's word chip (from
  `GET client` `overview.words`, the same source as Overview), ⋯ = `Move to project` (`MoveProjectModal`, as today).
  Empty: "No jobs in this campaign" / "Move a job here from another campaign."
- An ongoing project (General) uses the same page without dates and with the title-row action `Edit project`.
- No goal, result or "Record result" block (Sprint 5).

### 3. Campaign form (one component, modal; replaces the `Projects` editor)
Fields: Name, Type (campaign | ongoing; fixed after create), Stage (the funnel stage = `goal`; extra stages = `goals`,
as the current editor offers), Start, End (campaign only), Status (planned / active / paused / done), Client visible
(toggle). Create → `POST projects`; edit → `PATCH projects/:id`; server validation errors shown in the form. `Save` /
`Cancel`; this is the one form with a Save button on the client page (a campaign is created whole). `Projects.tsx` and
the Manage projects modal are deleted.

## Acceptance
1. Plan tab = title row, five-column stage board, off-stage line, milestones card, strategy documents card, as § 1;
   "We are here" only on the current stage and only when a campaign exists; empty stages read "Nothing planned".
2. Campaign cards: lines, status chip and `Open campaign` as § 1 B; a closed campaign reads "Closed <date> · n of n
   milestones".
3. Phone: one column, current stage first, other stages as rows; 44px controls; the lower grid stacks.
4. `New campaign` (owner) creates a campaign through the one form; `Edit campaign` on the campaign page edits it;
   server validation errors show in the form. `Projects.tsx` and the Manage projects modal are gone (no importer left).
5. Campaign page: fact strip, milestones with done toggle / add / edit / delete (confirm), jobs with the word chip and
   Move to project; works for an ongoing project too; no goal / result block.
6. The word chip of a job on the campaign page equals its word on Overview (one source).
7. Every function of the interim Plan tab has a home (the list in § 1 E, final placement in the PR body); reorder is
   the one function dropped, on purpose.
8. No calendar anywhere in this ticket.
9. Matches mockup 03 at EN 1440 light (without the calendar inset); AR words in the AR copy and tested (the live AR
   frame waits for a team language switch, as S3-02).
10. No migration; no API change unless a listed fact turns out missing (then: the smallest read-only addition, with a
    test and a line in `docs/DASH-API.md`, stated in the PR).
11. Checks green: web typecheck, `ds:check`, build, `test:api`; root typecheck, lint and `npx vitest run
    --no-file-parallelism` when anything outside `web/` changes.
