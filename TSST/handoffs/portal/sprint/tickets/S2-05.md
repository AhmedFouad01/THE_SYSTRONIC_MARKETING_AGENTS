# S2-05 — one `client_settings` row per client

Plan: "One row per brand: visibility flags, ui_lang, growth_report flag (off), optional account_manager_user_id and
requests_per_month if decided; one PUT; global defaults only in the packages catalogue." Acceptance: `endpoints.ts` has
one visibility writer; the client portal reads one source. Gate: decision (G0). Decisions 1–3 and 7 settled 2026-11-05;
4, 5, 6 run on their defaults since 2026-11-06 (Ahmed confirms at the deploy gate): no requests-per-month field, the
growth-report link only when the switch is on and a result exists, no "Approve all". Decision 3 (account manager per
client) needs its column here. Depends on S2-01 (merged).

## Design
### Server (migration `035_client_settings.sql`)
- `CREATE TABLE portal.client_settings (brand text PRIMARY KEY CHECK (brand ~ '^[A-Za-z0-9][A-Za-z0-9_-]*$'),
  show_package boolean NOT NULL DEFAULT true, show_billing boolean NOT NULL DEFAULT false, show_milestones boolean NOT NULL
  DEFAULT true, show_plan boolean NOT NULL DEFAULT false, client_tabs text[] NOT NULL DEFAULT '{image,video,copy,plan,files}',
  show_growth_report boolean NOT NULL DEFAULT false, ui_lang text NOT NULL DEFAULT 'en' CHECK (ui_lang IN ('ar','en')),
  account_manager_user_id uuid REFERENCES portal."user"(id) ON DELETE SET NULL, updated_at timestamptz NOT NULL DEFAULT now(),
  updated_by text NOT NULL DEFAULT '')`. No requests-per-month column (decision 4).
- Backfill, in the migration: one row for every brand known to the database (`brands`, `jobs`, `client_links`, and the keys
  of the visibility document's `brands`), with the values the client saw: the stored global merged with that brand's
  overrides (the document's `global` first, `DEFAULT_VISIBILITY` where a field is missing), `ui_lang` from `brands`. A
  brand with no row afterwards (a Drive folder nobody touched) gets the defaults from the code, which equal
  `DEFAULT_VISIBILITY` and `en`; the stored global is not consulted any more ("global defaults only in the packages
  catalogue"). The `visibility` settings row and `brands.ui_lang` stay in place, unread (dropped in S2-07's clean-up).
- `src/service/dash/client-settings.ts`: `ClientSettings` (the row plus `account_manager: {id, name} | null`),
  `DEFAULT_CLIENT_SETTINGS`, `clientSettingsOf(db, brand)` (row or defaults), `saveClientSettings(db, brand, patch, by)`
  (one upsert, `COALESCE` per field), `cleanClientSettings(body)` (every field optional; `account_manager_user_id` null
  clears, otherwise an active team user, 422 otherwise). `visibilityOfBrand` reads it; `Visibility` keeps its shape for
  every client reader, so the client portal changes nothing but its source. `brandProfile` reads `ui_lang` from it.
  `loadVisibility`, `visibilityFor`, `cleanVisibility`, `parseVisibilityDoc`, `VisibilityDoc`, `DEFAULT_VISIBILITY` go.
- Routes: `GET /api/v1/client/settings?brand=` (team) and `PUT /api/v1/client/settings?brand=` (owner, partial body, the
  one writer) answer the `ClientSettings` row. The team's client detail returns `settings` in place of `visibility`.
  Closed, 410 `gone` naming the new route (the S2-03c pattern): `GET|PUT /settings/visibility`, `GET|PUT
  /settings/clients/:brand/visibility`, `PATCH /settings/clients/:brand`.
### Web
- `endpoints.ts`: `getClientSettings(brand)`, `saveClientSettings(brand, patch)` replace the five functions; one writer.
  `ClientVisibility` and `ClientLanguage` call it (the toggles stay one field per save); the global Visibility page, its
  route and nav entry go (S3-03 redraws Settings anyway). Mock handlers for the two routes; the old ones go. Types:
  `ClientSettings`, `ClientSettingsPatch`.
### Tests
- `tests/v1-client-settings.test.ts`: defaults for an untouched brand; PUT saves each field alone and together, 422 on a bad
  value / unknown field / a user that is not an active team member, owner only; the client portal and `/client-auth/brand`
  follow the row (billing hidden, language); the five closed routes answer 410 and write nothing.
- `tests/migrate-035.test.ts`: rows with a global, two overrides, a brand only in `jobs`, one only in `client_links`,
  `ui_lang` on one: after the migration every brand has the effective values it had; an unknown brand reads defaults.
- The sixteen files that set visibility through the old routes move to `PUT /client/settings?brand=`; `v1-r99-language`
  moves to it too.
### Deploy notes
- 035 creates and fills one table; the old code neither reads nor writes it, so it is safe while the old code serves.
  A code-only rollback reads the old row and column again: changes made through the new route since the deploy are
  not seen until the code comes back (nothing is lost; the table keeps them). Say so in the deploy plan.
- Decisions 4, 5, 6 at the deploy gate: the defaults built here are "no requests-per-month field", "growth report off
  per client", "no Approve all". Changing 4 later is one column; 5 and 6 are S5 work.
