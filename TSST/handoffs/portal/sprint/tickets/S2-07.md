## Design
### A. Delete the old board and the dead decision path
- `app.ts`: `/legacy`, the `board.html` read, `/api/tree`, `/api/entry`, `/api/counts`, `/api/sync`, `/api/job`,
  `/api/text` go (they fall to the SPA 404 for API paths); `POST /api/decision` keeps its one-line 410 (documented as
  closed; an integration may still call it). `public/board.html` goes. `src/core/api.ts`: delete what only the board
  used (`apiEntry`, `apiCounts`, `apiText`, `CountCache`); `apiTree` / `apiJob` stay only if `src/cli/index.ts` is a
  live command (`package.json` bin or scripts) — otherwise the CLI file and they go too. `review-provider.ts` goes if
  nothing else imports it. `save-decision.ts`, `parseDecisionPayload`, `recordDecisions` go with `tests/decisions.test.ts`;
  `v1-cairo-day.test.ts` keeps its date assertions through the live item-decision route instead of `saveDecision`.
- The tests that exercised the old paths lose those assertions (or the test, when that was all it did); `spa.test.ts`
  drops `/legacy`; the 410 of `POST /api/decision` keeps its test. The PR lists every test removed or cut.
- `World.generalProjects` and its query go. S2-06's notes: `REVIEW_STATUSES` not exported, `reports.ts` header line
  dropped, `newest` and the three identical `idParam` copies in `shared.ts`. CSS rules with no user (`.r95-*`,
  `review-proposal*` and any the builder finds by grepping class names against the TSX) go.
### B. Round names → domain names (file names, identifiers, CSS classes)
- Server tests: rename by what they test (e.g. `v1-r99-language` → `v1-client-language`, `v1-r9d` → `v1-plan-visibility`,
  `v1-pkg4-credits` → `v1-package-credits`, `v1-simple-*` → by subject, `wipe-00*` → `wipe-brand`, `wipe-jobs` …); the
  builder reads each file's header to pick the name. Web tests the same. Mock modules by domain like the server
  (`r8.ts` → `commerce.ts` or what it holds, `r9.ts` → `clients.ts`/`plan.ts`, …) with `createR9` → `createClients` etc.
  Mock assets `r3-*`, `r6-*` → neutral names.
- CSS: the six files renamed by what they style; class prefixes mapped (`r9-profile-` → `profile-`, `r9-projects-` →
  `projects-`, `r9-review-` → `review-queue-` (collision check against `.review-card`), `r9-accounts-` → `accounts-`,
  `r97-requests-` → `requests-`, `r8-tools-` → `tools-`, and the rest found by grep), applied by one script to CSS and
  TSX together; the builder checks no new name collides with an existing class and that `web/qa/DS1` baselines
  (`ds:check`) still pass.
- Comment lines that cite a release or round as history (`DASH-API v1.13 R9 Part D`) stay: they name where a rule came
  from. The acceptance grep excludes comment lines.
### C. `DASH-API.md` matches the routes, by test
- `scripts/route-table.ts` gains `--md`: a Markdown table `| method | path | access | file |` (path = the regex source
  made readable, `([^/]+)` → `:id`), written into `docs/DASH-API.md` between two markers
  (`<!-- route-table:start -->` … `<!-- route-table:end -->`) at the end of the file; the hand-written history above
  stays. `tests/api-docs.test.ts` renders the same table from `ROUTES` and fails when the file's block differs.
  (The plan's "from route schemas": there are none; the route table is what the code can generate.)
### Kept for a later migration (not here, so a code-only rollback of the S2 block stays possible)
`brands.ui_lang`, the `visibility` settings row and its key, the 027 trigger/function and the `bridged` mark, the old
`decision_history` writers of the import tool. One migration after the S2 deploy settles; its ticket is written then.
