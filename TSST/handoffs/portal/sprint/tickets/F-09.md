# F-09: Deploy script safety (before the next release)

Why now: the evaluation re-run of 2026-11-23 (`sprint/evidence/S6-03-evaluation.md`) and the runbook read-through found that `scripts/deploy.sh` can leave the live site in a bad state in ways the script does not report. The next release is the largest so far (`next` is 327 commits ahead of live, with migrations 036, 037, 038). Size: medium, two pull requests. Gate: none to build; **nothing in this ticket deploys**. The first real use of the changed script is the next release, which needs Ahmed's own word.
Paths under `~/Work/tsst-portal` (`next` `21496e6`). Line numbers are of `scripts/deploy.sh` at that commit (168 lines; byte-identical to the script of 5 Nov).

## 1. What is true today (read from the script, nothing was run on a server)
1. **The health check is weak** (`:143-148`). Healthy means `/login` answers 200 and `/api/v1/me` answers 401 as JSON for an anonymous call. A release whose signed-in reads fail (a broken query after a migration, a missing table) still prints `healthy`.
2. **`--rollback` checks less** (`:31`): only `/login`, for 20 seconds.
3. **An automatic rollback leaves old code on a migrated database** (`:136` migrate, `:154-159` rollback). The script says so in one printed line (`:156`) and exits 1. Nobody has checked that the old code runs on the new schema (the runbook marks it "not verified").
4. **After a failed deploy `current` and `previous` point to the same release** (`:139` sets `previous` to the old release before the switch, `:158` puts `current` back to it). `--rollback` then swaps two equal links, and the release that failed is no longer reachable by a link.
5. **On a first deploy with no `current`**, a failed health check leaves the broken release live (`:158` runs only when `prev` is not empty).
6. **A release folder that already exists is deleted before it is rebuilt** (`:111`, `rm -rf "$R"`). If `$R` is the live release (redeploying the same commit) or the rollback one, the site runs from a folder that is being emptied; if `npm ci` then fails, `current` points at a half-built folder.
7. **The portfolio file on the server is replaced first** (`:110`), before the dump, the migration and the switch. No rollback restores it.
8. **The pre-deploy dump is taken while the app is running** (`:125-131`). It is a consistent `pg_dump`, but writes made between the dump and the switch are not in it.
9. **No check runs before the upload**: no typecheck, no test, no lint (`:74-93` only builds the web and scans the build).
10. **Defaults inside the versioned file** for the key path, the host and the portfolio path (`:16-18`; the values are not copied here), and the same in `scripts/pull-backup.py` (`:29-31`). The header says "from this PC (Git Bash)" (`:2`); the deploy runs from the Mac.
11. **The script ships only `origin/main`** (`:46-60`).

## 2. Design
### 2.1 Pull request a: the script
- **Refuse before anything changes on the server** (new checks at the top of the remote part, before `:110`):
  - `$R` equals the target of `current` or of `previous`: stop with a sentence that says which, and that a release is never rebuilt in place. A new flag is NOT added to force it.
  - The backups folder is missing (today checked at `:122`, after the portfolio install): move the check up.
- **Order**: portfolio install moves to after the migration and before the switch, and the old file is kept as `portfolio.yaml.previous`; an automatic rollback and `--rollback` put it back.
- **Health check, one function used by the deploy and by `--rollback`**:
  - today's two answers, plus
  - `GET /api/ping` (exists) answers 200, and
  - a database read that needs no session: a new tiny route is NOT added; the check runs `scripts/migrate.ts --status` (a new read-only mode of the existing script: prints applied and pending names, exits 0 only when nothing is pending and the names match the release's files) as the service user. Pending or unknown names fail the check.
  - The limits are printed: "healthy means: the shell loads, the API refuses anonymous calls, the database holds exactly this release's migrations. It does not prove any page works: do the smoke list."
- **Rollback state**: on a failed health check the script sets `current` back and leaves `previous` as it was BEFORE the deploy (so the two do not become equal), records the failed release name in a file `last-failed` next to the links, and prints the three names. On a first deploy with no `current`, it stops the service instead of leaving a broken release live, and says so.
- **After an automatic rollback that followed a migration**, the last lines printed are a block, not one line: the names of the migrations that were applied, "old code now runs on the new schema", the dump name, and "read RUNBOOK section 5 before doing anything else".
- **Checks before the upload**: `npm run typecheck`, `npm run lint`, and the web `typecheck`, in the working tree being released; a failure stops the deploy. The full test suite is NOT run by the script (10 minutes; the runbook's section 3 stays the place for it) but the script prints the commit and asks for one typed word (`deploy`) before the upload, unless `TSST_YES=1` is set. A release that contains new migration files prints their names in that prompt.
- **No defaults in the file**: `TSST_KEY`, `TSST_HOST`, `TSST_PORTFOLIO` are required; a missing one stops the script with its name. Same for `scripts/pull-backup.py` (`--key`, `--host` or the environment). The header says which machines it was used on, without paths.
- **Not changed**: what the script uploads, the dump format, the retention counts, the atomic link swap, the open-PR and `origin/main` checks, `--dirty`.

### 2.2 Pull request b: tests and the runbook
- **A harness that runs the remote part without a server**: the remote part moves into one file `scripts/server/deploy-remote.sh` that takes its root (`P`) from an argument, default the real path; `scripts/deploy.sh` sends that file. A test (`tests/deploy-remote.test.ts`, bash through `execFile`) runs it against a temporary folder with stub commands on `PATH` for `systemctl`, `curl`, `pg_dump`, `npm`, `sudo`, `install`, `journalctl` and a fake `migrate` that can be told to pass, fail, or pass and then make the health check fail.
- Cases, each asserting the links, the files and the printed lines: a clean deploy; migrate fails (nothing switched, portfolio untouched); health fails after a migration (current back, previous unchanged, `last-failed` written, the block printed, exit 1); first deploy fails (service stopped); `$R` equals current (refused, folder untouched); `$R` equals previous (refused); backups folder missing (refused before any change); `--rollback` after a good deploy and twice; `--rollback` after a failed deploy (clear message, nothing swapped); portfolio restored by both rollbacks; retention keeps current and previous; a missing `TSST_*` variable.
- `bash -n` and `shellcheck` (if installed; else the test says it was skipped) on both scripts.
- `docs/RUNBOOK.md` sections 2, 4, 5, 6 and 9 updated to the new behaviour, every changed sentence re-read against the script; the "hazards" warnings that no longer apply are removed, not left as history.
- The harness proves the logic, not the server: the ticket's build record must say that the changed script has NOT been run against the real server until Ahmed orders a release.

## 3. Acceptance
1. Every case of 2.2 passes; the test fails when the fix it covers is reverted (shown for at least the health-fail and the `$R` equals current cases).
2. A deploy of a release whose folder is the live or the rollback one stops before any file on the server changes.
3. A failed health check never leaves `current` equal to `previous` unless they were equal before, and never leaves a broken first release serving.
4. The health check fails when the database holds a migration the release does not have, or lacks one it has.
5. The portfolio file is the old one after any rollback.
6. No key path, host or address default in either script; `git grep` for the old values in `scripts/` is empty (the values are checked by the builder against the current file, never written into a ticket, a commit message or a test).
7. `--rollback` and the deploy use the same health function.
8. The runbook matches the script; a fresh reader finds no step that contradicts it.
9. Root typecheck, lint, full suite, `bash -n`: green. Nothing was deployed.

## 4. Not in this ticket
The release itself and its stages. The rehearsal of migrations 036 to 038 on a restored copy (its own step, needs Ahmed's approval). CI on GitHub (billing, Ahmed's). Monitoring between deploys. Stopping the app during the dump (a product decision: it means a short outage on every deploy; see Q2). Running the full suite inside the deploy. A second server or a staging site. Any change to `SERVER.md`.
