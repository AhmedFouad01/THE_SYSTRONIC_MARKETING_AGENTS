## 3. The read model
**One answer: `GET /api/v1/home/today?view=mine|everyone`** (access `team`; `view` defaults to `mine`; `everyone` by a member = 403 `forbidden`, anything else 422). Built in `src/service/dash/home.ts`, route in `work.ts` next to `home`.
```
{ today, viewer:{id,name,role}, view,
  counts:{needs_action,due_today},
  needs_action:[{ brand, brand_name, stage, rows:[Row] }],       // Everyone: every live client (empty rows = calm); Mine: clients with rows
  due_today:[Row],                                               // tasks only
  waiting:[{ with:{id,name}, count }],                           // Mine only
  next_due:{ title, due, brand_name }|null,                      // only when both lists are empty
  new_requests:[JobRequest]|null,                                // null for a member
  attention:{ no_maker, blocked }|null }                         // owners only
Row = { kind:'job'|'task', id, brand, job|null, title, version|null, project_name|null, type|null, items, in_row,
        step:'changes'|'review'|'approval'|'overdue'|null, status, days, with:{kind,id,name,you}, with_more, made_by|null, due|null, done }
```
- Core, shared with S4-07: `homeFacts(db, world, {viewer, view, from, to, today})` -> `{turns, tasks}` (turns for every step incl. planned / ready; tasks from one `listMilestones` window plus overdue). Today = `todayRows(facts)`; Week will be `weekRows(facts)` over the same facts. The Mine filter is `needsAction` ∩ steps (`changes|review|approval`) plus tasks `owner = me`; Everyone = every turn in those steps (`everyone()` grouping not needed: rows carry `with`) plus every owned task.
- **Query budget** (beyond the `loadWorld` / `scanAll` GET /home already does): `turnsOf` 5, `listMilestones` 1 (window today..today+30 with overdue; Due today, Next and overdue are cut in memory), `listJobRequests` + deleted brands 2 (owner only), `stagesByBrand` 1: at most 9, independent of items, jobs or clients. Project names and types come from the world/cards (how project names sit in the world: not read; if not in memory, one query on `portal.projects` for the brands in scope). Test: a query recorder, same count for 1 and 8 items and for 2 and 5 clients.
- **A client without a review order** (every real client now): its items read `review` with the earliest active owner and `approval` with the client; `changes` with no maker is the owners group, so every active owner has it on Mine and a member sees it only when they are the maker. A Drive-made item has no maker, so **a member's Mine is nearly empty until makers are set** (consequence of Decision 13, Q2); the owner sees the count in `attention`. Review for an unordered client shows only for the earliest owner on Mine; other owners see it on Everyone (Q3). Rows say "with <name>" always; no row is ever without a name.
- **Counters move to the turn (PR b):** one definition `pending review = turns at step review or held` (what `/review` `needs_team_review` already is for an ordered client, `approvals.ts:359-388`). Changed: `kpis.pending_review` (`work.ts:638`), the `pending_review` bucket (`home-today.ts:40`, held and planned handled as above), `client_changes` bucket (turn `changes`), `itemCounts.pending` for team cards (an optional `turns` argument; `jobs.ts:662`), `JobWordItem.pending_review` (`job-word.ts:118`). `changes_requested` / `approved` counts stay (nothing in the web reads them). Parity test, both kinds of client: Home KPI = sum of job-card `counts.pending` = number of `/review` rows with queue `needs_team_review` = rows of `todayRows`' review turns; the differences that remain by design (an unordered item the team approved but did not send reads `review`; a held item is counted) are listed in the test, not hidden. The unordered numbers are pinned by a recorded transcript as S4-00 e2 did.
- **Old `GET /home` stays** (callers above): same keys and shapes; `kpis.pending_review`, `today` and `today_counts` change numbers by the rule above; `requests`, `milestones`, `campaigns`, `packages` unchanged. The Home page stops reading it; the old buckets are removed in a later cleanup, not here. Health stays on `clientReviewFacts` (parity test already pins `waiting` and `owed`); moving it is not needed by any screen.
