## 1. What is true today
- **The stable address of a client item** is `/client/for-your-review?item=<id>` where `id` is the item's uuid (`portal.items.id uuid`, migration 027:23-24). Every "Open" in the client pages builds it: `web/src/lib/clientItems.tsx:64`, `ClientHome.tsx:106` and `:118`, `ClientWork.tsx:70`. The page reads the `item` parameter (`ClientReviewQueue.tsx:31-34`, `:49`) and looks the item up in the queue AND in the full "my work" list (`pool`, `:54`), so an item that no longer waits still opens. What the page shows for an id that is not in the client's lists (another brand, a hidden item, an unknown id): not read.
- **Opening that address signed out does NOT lead to the item after sign-in.** Two facts:
  1. `ClientShell` reads the viewer first; a 401 shows the "invalid link" page and nothing else, no sign-in form (`ClientShell.tsx:73-76`: `viewer.error` 401 renders `InvalidLink`).
  2. Every sign-in ends on the same place, with no return target: password sign-in `navigate('/client')` (`ClientSignIn.tsx`, `PasswordSignIn`), code sign-in `window.location.replace('/client')` (`CodeSignIn`), the already-signed-in redirect `navigate('/client')`, and the PIN gate `window.location.replace('/client')` three times (`PinGate.tsx:32`, `:41`, `:52`). I found no `next`, `returnTo` or `redirect` parameter in the client pages. So the plan's acceptance "link opens the item after sign-in" is a CHANGE, not a check.
- **The client's sign-in address is `/c/<slug>`**, the brand's slug (`portal.brands.slug`, migration 016:3-6; the page asks `GET /client-auth/brand` which is a public route, `clients.ts:527`, and shows only the brand name, logo and language). `ClientEntry` chooses the page by the shape of the last segment: exactly 43 characters of `[A-Za-z0-9_-]` is a LINK TOKEN and opens the PIN gate; anything else is the slug sign-in (`ClientSignIn.tsx`, `ClientEntry`). A link token can open a client's workspace, so it is a credential. The slug is not (it is the public sign-in address, it grants nothing).
- **Access check on the server.** Client routes answer 401 with no active client session (`guard.ts:22-26`); the item routes are `client` access (`work.ts:245` versions, `approvals.ts:322` decisions). That an item of another brand answers 404 on each of them: not read (acceptance 6 pins it).
- **What the team knows about the item.** Whether an item is one "the client can see" is decided by the same predicate the client reads use (`itemVisible` in `job-model.ts`, used by `client-view.ts` and `turn.ts`: file and line not read), plus `sent_version`, `withdrawn`, the job not archived or deleted, and a project not hidden from the client (`ItemTurn.hidden_from_client`, `job_closed`: `turn.ts:96-100`). Which field of a team item payload the web can use for this today: not read.
- **The public origin for links**: `deps.origin()` = `PUBLIC_ORIGIN`, else the checked Origin header, else the Host (`src/server/v1/core.ts:111-112`).
- **No phone number of a client person is stored anywhere.** `portal.client_people` has id, brand, email, name, role, status, invited_at, last_sign_in, last_seen and the password columns (migrations 016 and 019); a search of all migrations for `phone` and `whatsapp` finds nothing. The only phone in the code is the workspace's own company phone for documents (`documents.ts:25`, `workspace.ts:219`), which is not the client's. So a wa.me link with a number cannot be built from data; it is text only.
- A search of `src/` and `web/src/` for `wa.me` and a WhatsApp sender finds none.

## 2. Design
### 2.1 The link (what it contains)
`<origin>/c/<brand slug>?next=<URL-encoded "/client/for-your-review?item=<item uuid>">`
- origin, the public sign-in address of the brand, the item's address. **No token, no PIN, no code, no setup link, no password, no session id, no email, no person id.** The uuid is an identifier, not a credential: access always needs a signed-in client person (or an unlocked link) of the SAME brand; the server decides, so a copied link that reaches another person shows what that person may see, or the empty queue.
- The builder refuses to make the link when the slug has the shape of a link token (43 characters of `[A-Za-z0-9_-]`): the action answers "not available" rather than put a credential in a message.
### 2.2 Sign-in returns to the item (web, client pages)
- A pure function `safeNext(raw)` in `web/src/lib/clientAccess.ts` (node test): accepts only a string that starts with `/client` followed by `/` or `?` or end, with no `//`, no backslash, no scheme, no control characters, at most 300 characters; anything else is `/client`. (An open redirect is the risk.)
- `ClientSignIn.tsx`: read `next` from the address once, and use `safeNext(next)` in place of `/client` in the four places above (password, code, already-signed-in, and after the first password SETUP when the setup page was reached with `next`: default the setup keeps going to `/client`, Q4). `PinGate` is NOT changed: a link-token address is not the shared form.
- A signed-out visit to `/client/for-your-review?item=...` directly stays the "invalid link" page (the slug is unknown there); that is why the shared address is the `/c/<slug>` form.
- The item not visible to the person who signed in: the page lands on the queue with no item selected and no error that tells whether the item exists (default; the builder reads what the page does for an unknown id today and keeps it).
### 2.3 The read that makes the message (new, team only, GET, `src/server/v1/work.ts`)
`GET /items/:id/share` (team access; any member and the owner; a client link is 401 as on every team route) answers
`{ can_share: boolean, reason: null | "not_sent" | "withdrawn" | "hidden" | "closed" | "no_client_person" | "slug_unsafe", item_id, title, brand_name, url: string | null, lang: "en" | "ar" }`
- `url` as 2.1, built with `deps.origin()`; `null` when `can_share` is false.
- `can_share` is true only when the item is one the client can see now (the predicate of section 1) AND the brand has at least one active client person (`status = 'active'` or `'invited'`: a person who can sign in; the builder picks by reading how sign-in checks it). Otherwise the `reason`.
- `lang` is the client's language (`ui_lang` of the client settings row, the one the client header uses), so the text is in the language the client reads.
- It writes nothing (no row, no activity, no history), makes no outbound call and sends nothing. It is the only server part.
### 2.4 The control and the text (web, team; waits for the drawing)
- One quiet text action on a team item (the menu of an item row on the Job page; exact place from the drawing): "Copy WhatsApp message". Shown only when `can_share`; for an item that cannot be shared the action is absent, except `no_client_person` where it is disabled with the reason in words (so the team knows to invite a person).
- On press it calls 2.3, builds the text below and the link `https://wa.me/?text=<URL-encoded text>` (text only, no number: the team member picks the contact in WhatsApp), and does two things the person can see: copies the message text to the clipboard and opens the wa.me link in a new tab (`rel="noopener"`). If the clipboard is refused the text is shown in a small box to copy by hand. The web never calls a send endpoint (there is none).
- The text, ready, a placeholder for Ahmed's reading (Q2):

| Language | Text (`{title}` the item title cut at 80 characters, `{url}` as 2.1) |
|---|---|
| English | `Hello! "{title}" is ready for you to review. Open it here: {url}` |
| Egyptian Arabic | `أهلاً! «{title}» جاهز عندك للمراجعة. افتحه من هنا: {url}` |

  Nothing else goes in the message: no price, no team name, no internal note, no status of the team's own steps, no file path.
- Words of the action and its states in `copy.th` EN + AR (team pages have no language switch; both languages tested in a node test); the message text lives in the same file as a function, not in the page.

## 4. Acceptance
1. Access: 401 with no session, 401 for a client link, 200 for a member and an owner; an unknown item id 404; an item of a deleted client 404.
2. `can_share` per case: sent and visible true; never sent, withdrawn, job archived or deleted, project hidden from the client, delivered-and-closed job (what "closed" means for the client reads: the same as `ItemTurn.job_closed`) false with the right `reason`; a brand with no active client person `no_client_person`.
3. The URL: exactly the form of 2.1 (a test compares the string with `new URL`): origin, path `/c/<slug>`, one `next` that decodes to `/client/for-your-review?item=<uuid>`, nothing else. A scan of the whole answer for `token`, `pin`, `code`, `setup`, `password`, `session`, `@` finds nothing; a slug of 43 URL-safe characters gives `can_share: false`, `reason: "slug_unsafe"`.
4. **No message is sent by the system:** the route and `share-link.ts` import no HTTP client, mail, queue or provider module and call no `fetch`; a source-scan test fails otherwise; the route is GET and a test counts every table before and after (no row written anywhere, no activity or history row); no provider, key or setting for WhatsApp is added (`.env.example` and settings unchanged).
5. `lang` is the client's language; a client whose language is Arabic gets `ar`.
6. Brand wall: a client signed in to brand A who opens the item of brand B by address gets the same answer as for an unknown id (404 on the item routes, no title, no brand name in any answer); test against `client-view/items/:id/versions` and `…/decisions`.
7. `safeNext` accepts `/client`, `/client/for-your-review?item=<uuid>`, `/client/work?type=posts`; refuses `//evil.example`, `https://evil.example`, `/\evil`, `javascript:`, `/clients/view`, `/client/../c/x`, a string with a newline, one over 300 characters; each refusal gives `/client`.
8. Gate `web/qa/S6-02/gate.mjs` on the mock build (both sign-in styles): signed out, open `/c/<slug>?next=...`; sign in by password; the item is open in the review page. Same with the email code. Already signed in: opening the link goes straight to the item. A `next` that is not allowed lands on `/client`.
9. The link of a client signed in as a person of another brand lands on that brand's own place and shows nothing of the other item (no error naming it).
10. The action is on a team item only when `can_share`; a member and the owner both see it; it is absent on every client page (a gate case lists the client pages and finds no WhatsApp control or text).
11. Press: the clipboard holds exactly the text of section 2.4 in the client's language with the link; a new tab opens `https://wa.me/?text=` followed by the encoded text; no number in the address; the page makes only the one GET of 2.3 (the gate counts calls: no POST, PUT or PATCH).
12. 390 and 1440, light and dark, EN and AR team copy: the control is 44px under 768, in the drawing's place, no sideways scroll, text 4.5:1, no stroke, no hex colour; the disabled state shows its reason in words.
13. Checks green: root typecheck, lint, full suite with `--no-file-parallelism`; web typecheck, `ds:check`, build, `test:api`; older client gates stay green (F-04, F-08, S5-04); `tests/client-payload-walk.test.ts` untouched.

## 5. Not in this ticket
Sending a message by the system, a WhatsApp Business account, a provider, a webhook, delivery or read marks. A phone number field on a client person (no data today; a number would also be personal data: its own ticket and decision). A bulk "message the client about everything waiting". A message from the client side. A shareable link that opens the item without sign-in (a link carrying access by itself is forbidden here). Notifications. Changing the 43-character link tokens or the PIN gate. Deploy.

## 6. Owner questions (defaults let the server part and the sign-in return proceed)
1. Where the action sits and what it looks like: the drawing in `mockups/s6/` decides; the web part waits for his word.
2. The two texts above are placeholders for his reading (tone: "Hello!" and "أهلاً!"; whether to name the client person; whether to name the brand). Default: as written, no name.
3. A client phone number: default none (text only, the team member chooses the contact in WhatsApp).
4. After a person's FIRST password setup, should the return also apply? Default no (setup lands on `/client`).
5. Who may use the action: default every team member and the owner (the same people who can open the item).
6. The viewer role of a client person gets the same link as an approver (they sign in and see the item; the approve bar stays hidden): default yes.
