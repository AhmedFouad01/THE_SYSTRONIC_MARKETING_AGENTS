## 3. Design of the written parts
### 3.1 `docs/RUNBOOK.md` sections
1. **What this is and who may do what** (the owner decides a deploy; nothing in this file starts one).
2. **Before you start**: what you need on the machine (Node version from `package.json`; GNU `tar` and `grep` first on `PATH` on a Mac, as the BOARD says; the key and the host come from the environment, set as `SERVER.md` says: see there), and what you must not do (no `--dirty` for a release, no `TSST_ALLOW_OPEN_PRS` without the owner's word).
3. **Checks before a release**: the commands and what green means (typecheck, lint, the full suite with `--no-file-parallelism`, web typecheck, `ds:check`, build, `test:api`, `scripts/check-live-build.sh`, the route table test); migration list since the last deploy and the rehearsal (section 4.3).
4. **Deploy**: the steps of the script in order, what each prints, the owner's word first, the same-day backup, one command, the live smoke list (the list of the S5/S6 parts; the smoke of each older step is on its deploy ticket).
5. **Rollback**: (a) code only, `--rollback`, what it does, and that running it twice returns to the newer release; (b) when a migration ran: the release is rolled back AND the database restored from the pre-deploy dump (the migrations are forward-only); (c) to the release before the sprint (tag `v-before-sprint`); what is lost in each (data written after the dump). For migrations 036 to 038: whether a code-only rollback is safe after them: not read; the rehearsal answers it and the runbook states the answer.
6. **Restore**: from a nightly dump and from a pre-deploy dump; the order (stop the app, load, start, check); where the steps live (`SERVER.md` "How to restore a backup": reference, never copied) and the limits of the 2026-11-06 drill (not media, not secrets, not a server rebuild).
7. **Backups**: what runs nightly, what the deploy adds, the owner's off-server pull (`scripts/pull-backup.py`, how often, how to check it ran).
8. **Migrations**: forward-only, how to add one, how the deploy applies them, how to check the applied list.
9. **Health and first aid**: the two health checks, the logs and the service name (see `SERVER.md`), who to call.
10. **Glossary of the release names** (`current`, `previous`, `-dirty-`), and the meaning of "healthy".
Each command in the runbook is copied from `deploy.sh`, `package.json` or the BOARD and the PR lists where (acceptance 2).
### 3.2 What "a new developer deploys from the runbook alone" means here
No deploy is made to prove it. The proof is a **read-through with no other file open** by a reviewer who did not write it (a fresh agent given only the runbook and the repo): it lists every step it could not do or had to guess, and the runbook is fixed until the list is empty. Plus `bash -n scripts/deploy.sh` and a `--help` style check that every command in the runbook exists (acceptance 3).

## 4. The gate: the deploy
**The deploy is NOT part of any pull request above and does not start until all of these are true and written in the build record with their evidence:**
1. **Ahmed's explicit word in chat that day** for this deploy ("نعم انشر" or equal), naming what is deployed (`next` at an exact commit) and the night (quiet hours; the plan used Cairo 01:00 to 06:00). A word on another day or for a different commit does not count (BOARD "Deploy": each step needs its own OK).
2. **A backup the same day**: the nightly dump of that day exists and the off-server copy was pulled and verified that day (`pull-backup.py` ran and its dump gzip-verified); the deploy then writes its own pre-deploy dump before migrating and aborts if it cannot.
3. **The rehearsal of migrations 036, 037 and 038 on a restored copy of the production database.** This needs Ahmed's separate approval because a copy of the real data (client emails and names) leaves the server: where it is restored (a local database on the Mac, nowhere else), who may open it, and that it is deleted after, are written before it starts. Steps: pull the newest verified dump; restore it into a throwaway local database; run `scripts/migrate.ts` of the release; run the full suite's database tests and the two scenario scripts if they apply (`scripts/migration-003-scenario.ts` is old: the builder checks whether any scenario for 036 to 038 exists, else writes the three checks of 3-a); open the app against it and walk Work, a job, the Week, a campaign page with goal and results, the client home and report; **also exercise the rollback**: restore the same dump again and run the OLD release against the migrated database to learn what a code-only rollback does after 036 to 038. Record the timings (the first start after the deploy syncs every job: S2-03b).
   - 3-a, the three checks if no scenario exists: counts of the touched tables before and after; no change to a row the migration does not own; the new tables empty or as the migration says (038: goals, results, notes; 037: the `week` settings row; 036: makers, review order, the `action` list).
4. **The runbook reviewed (the read-through of 3.2 is empty) and the evaluation re-run (PR d) attached.**
5. **Checks green on the exact commit** (the same list as 3.1 step 3). GitHub CI is blocked by billing: the local run is the record, Ahmed's word on it as for each merge.
6. **`main` at that commit**: `next` merged into `main` by pull request, the way DEPLOY-PLAN did (the script refuses another checkout). Ahmed's word is needed for the merge too.
7. **The firewall step by Ahmed** (his public address in the SSH rule); the loop never touches the cloud account.
8. Roll-forward and rollback written for THIS deploy before it starts: which of the rollback forms applies after 036 to 038 (from the rehearsal), who decides, and the stop point after which the database restore is the only way back.
After the deploy: the live smoke, the health check, the pre-deploy dump's name in the build record, `BOARD.md` closed with the end state (live commit, migrations applied, what is live, what is not, the open list and the second-sprint boundary from the plan: baselines, next move, spend, import, profitability), and a note in `tickets/` of what the first start cost.
