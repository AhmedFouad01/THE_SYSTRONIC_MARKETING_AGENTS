# S1-04: "today" is the Cairo day everywhere

Part S1 (safety). Gate: none. Depends on: S1-03. Approved by Ahmed 2026-11-06.
State lives on `../BOARD.md`; this file holds the scope, the acceptance list and the evidence.

## Problem
"Today" was the UTC date in the server and in the web app; only the reports used Africa/Cairo. Between midnight and
02:00 in Cairo (03:00 in summer) the UTC date is still yesterday. In those hours a post scheduled for the new day was
not "out today", a milestone due the day before was not overdue yet, a time entry got yesterday's date, and on the
first night of a month the package window was still the old month. Days of events (a decision, a payment) were cut
from the UTC date too, and the web showed clock times in UTC (two or three hours behind Cairo).

## Scope
Repo `~/Work/tsst-portal`, branch `sprint/s1-04-cairo-today`, worktree `~/Work/tsst-portal-s1-04`, PR into `next`.

- **Server:** `src/core/day.ts` (new) holds the one rule: `dayOf(instant)` and `todayOf(now)`, Africa/Cairo.
  `src/service/dash/dates.ts` re-exports it, so every `todayOf` caller changes at once. The 14 lines that cut the UTC
  date out of a time now call `dayOf` (package windows and credits, time summary, requests, reports, the client
  timeline, the decision date in the old review shapes). Month ends use calendar arithmetic. Days cut inside SQL
  (the lifetime window start, the client activity from / to filter) use the Cairo zone; they followed the database
  session zone, which is the machine's zone on the embedded test database. `dayOf` refuses a missing time.
- **Web:** `web/src/lib/day.ts` (new) is the same rule. `todayIso()` is the Cairo day, and every formatted date
  (`formatDay`, `formatDayYear`, `formatMonth`, `formatDateTime`) shows a real time as its Cairo day and clock. A plain
  day is never shifted.
- **Docs:** `docs/DASH-API.md` and `docs/DASH-REPORTS.md` say "today" is the Cairo day (they said UTC).
- **Tests:** `tests/v1-cairo-day.test.ts` (11 tests: 00:30 Cairo in winter and summer, the summer-time switch days,
  team Home, time entry, first night of a month, time summary, client timeline, saved decision, and a guard that fails
  when a server file cuts the UTC date again); web: `day.test.mjs` and `format.test.mjs` (8 tests; `test:api` now also
  runs `src/lib/*.test.mjs`).

Left out on purpose:
- The mock API (`web/src/api/mock`): its own fixture world.
- A client link's `expires` given as a day still means the end of that day in UTC (02:00 or 03:00 Cairo of the next day).

## Acceptance
1. One helper decides the day (`src/core/day.ts`), right in winter (UTC+2) and in summer (UTC+3).
2. No server file under `src/` cuts the UTC date out of a time, except calendar arithmetic in `dates.ts`; a test guards it.
3. Tests at 00:30 Cairo pass, and fail with the old UTC day.
4. The web uses the same rule for today, for the day of an event and for clock times.
5. `docs/DASH-API.md` no longer says today is UTC.
6. No API shape change, no migration, no new dependency, no UI structure change.
7. Checks green: root typecheck, lint, the whole suite; web typecheck, `test:api`, `ds:check`, live build.

Plan wording kept for the record: "No `new Date().toISOString().slice(0,10)` outside the helper" = acceptance 2;
"Waiting-days test passes at 01:00 Cairo" = acceptance 3 (the reports' `waiting_days` count whole 24-hour periods and
were never tied to the date, so the tests cover what did depend on the date).
