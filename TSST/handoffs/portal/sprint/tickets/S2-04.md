## Design
### Server (migration `034`)
- `deleted_at timestamptz` on `bonuses`, `brand_packages`, `document_payments`, `milestones`. No backfill, no index
  (small tables), a 5 second lock timeout as in 032 and 033.
- The four delete routes set `deleted_at` (the time of the request) instead of removing the row. Same answers as
  today: 404 for an unknown or already deleted row, 204 on success, the package's 409 unchanged.
- What the foreign keys used to do, done by the code in the same transaction:
  - a deleted package: `jobs.package_id` of its jobs is set to NULL (as `ON DELETE SET NULL` did). Its `payments`
    rows stay: they are only reachable through the package, which is hidden; the 409 still guarantees none is paid.
  - an undone document payment: the route already clears the dues and their `document_payment_id`.
- Every reader listed above filters `deleted_at IS NULL`; a write on a deleted row (PATCH a deleted bonus or
  milestone, attach a job to a deleted package, a document payment against a deleted package) answers 404 as for a
  row that does not exist.
- No restore route in this ticket (030 has none either). The row stays for history and for a later restore.

### Web
- One component is the only place that calls a delete function: `ConfirmDelete` (name to settle in the build), built
  on the existing `ConfirmModal`: it takes what to say and the call to make, shows busy and the error, and closes on
  success. The 13 hand-made dialogs move to it; their words stay.
- A check in the web test run fails when a delete / revoke / archive API function is called outside that component
  (the list of functions is read from `api/endpoints.ts`, so a new one is covered).
- `endClientPreview` is exempt and named in the check (it ends a session). `PostWizard`'s reset path is traced in
  the build and either goes through the component or is shown not to be reachable without a confirmation.

### Tests
- For each of the four tables: after the delete the row is still in the table with `deleted_at`; it is gone from
  every list and count that showed it (named per table in the test); a second delete and a later edit answer 404.
- Package: its jobs lose `package_id`; the 409 on a paid payment still holds; its dues do not show anywhere.
- Migration test for 034 (columns added, existing rows untouched), as for 031 to 033.
- A source check: no `DELETE FROM portal.(bonuses|brand_packages|document_payments|milestones|client_links|payments)`
  in `src`.

### Deploy notes
- 034 only adds nullable columns: safe while the old code serves (deploy.sh migrates first). The old code keeps
  hard-deleting until the switch, which loses nothing new.
- Rollback to the old code after rows were soft-deleted: the old code does not know `deleted_at` and shows them
  again. To say in the deploy plan.
