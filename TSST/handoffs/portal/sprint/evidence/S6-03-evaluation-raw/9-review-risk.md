## 2. Migrations on a database with real rows

**036** (`migrations/036_makers_review_order.sql`). Adds columns, 2 CHECKs and a FK on `items`, `item_decisions`, `item_events`, `client_settings`, `job_meta`; replaces a view (`:75`); swaps the action CHECK (`:85-97`); one backfill (`:103-113`). All in one implicit transaction, so the first ACCESS EXCLUSIVE lock on `items` (`:36`) is held until the end, through the backfill. `items` is blocked for reads and writes for the duration; length scales with rows, which I cannot tell (the backfill is one hash join, probably seconds). New FKs to `portal."user"` (`:37,40`) also lock that table against writes. Each lock waits at most 5 s (`:33`); a waiting exclusive lock queues readers behind it for that time.
- **Lock timeout trips:** the whole file rolls back (`migrate.ts` single query), the runner throws, `set -e` stops the script at `deploy.sh:136`, before the switch (`:140`). Old code keeps serving. Left behind: new portfolio file, release folder, dump. Retry is safe. If 036 passes and 037 or 038 fails, 036 stays; that is still safe for old code (below).
- **Backfill guess:** `maker_user_id` = the one user whose name equals `items.created_by`; for "Drive sync" items, `posts.created_by` (`:107`); ambiguous or unknown stays NULL; disabled and deleted users count (`:101-102`). Wrong cases: a Drive item whose post author is not its maker; a name of a person who left. Effect: none for a client while `reviewer_user_id` is NULL (header `:2-3`). After a client gets a reviewer: the true maker gets 403 `not_maker` on send/recall (`maker.ts:105,128`; an owner can override), and a reviewer wrongly named maker is "out" for that item (`review-order.ts:210-213`) so it waits with no reviewer. A delay, not an exposure. The switch-on preview counts `no_maker` and `maker_is_reviewer` (`review-order.ts:200-225`): read it before every switch-on.
**037**: one CHECK widened on a handful-of-rows table, sub-second (`:15-18`). **038**: three new tables, three FKs to `projects` (SHARE ROW EXCLUSIVE: reads continue, writes to `projects` wait) (`038:5-6`). No backfill.
**Safe while OLD code serves:** yes by reading: additive, nullable or defaulted columns; old inserts name their columns (`job-model.ts:177,282` @6a28ba3; `client-settings.ts:126` @6a28ba3).

**Old code on the new schema (the runbook's "not verified").** Best reading: it runs, about 80% sure for the schema alone. Evidence: (a) old `migrate.ts` loops over files on disk and ignores recorded names it has no file for, so it boots on a database with 036-038 recorded (`migrate.ts` @6a28ba3); (b) `SELECT *` on `current_item_decisions` and `item_events` (`work.ts:252,444` @6a28ba3) returns new columns only to team routes; the client mapping is an allow-list (`clientModelItem`, `job-model.ts:451-515` @6a28ba3), so no new id leaks; (c) it never deletes `items`/`item_versions` (grep found none), so the deferred FK `items_submitted_version_fk` cannot trip; (d) it reads settings by key (`branding.ts:132`, `documents.ts:42`, `jobs.ts:197` @6a28ba3), so a `week` row is ignored; (e) project delete cascades 038 tables away. Lower confidence (about 50%) on meaning: after a client has a reviewer, old code ignores review order and "submitted" marks, so items may reach the client sooner than the team intends. Only a rehearsal settles it.

## 4. Script hazards a single big release worsens
- Thin health check (`:143-148`) and no tests in the script: more change, more chance it passes while pages fail.
- Auto-rollback pointer bug (`:139,158`): more likely to be used.
- Dump with app running: the window is the migrate time; a long 036 widens it.
- `rm -rf "$R"` (`:111`) hits when the name equals `current` or `previous`: staged releases and retries make that mistake easier, so fix it before staging.
- Portfolio replaced first (`:110`): same in any plan; pass the right file.
