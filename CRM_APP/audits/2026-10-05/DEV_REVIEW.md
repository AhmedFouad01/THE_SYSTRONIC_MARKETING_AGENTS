## 3. Test-quality verdict (SK-011): PARTIAL, proves models, not product behaviour
- Strong: pure view-models are well tested (gridModel, savedViews, useCursorList reducer, session, client headers/idempotency, static path traversal with 20 hostile inputs, i18n parity, token parity). 197 unit tests pass on HEAD.
- Weak 1: component tests are `renderToString`/`renderToStaticMarkup` only (5 files). No DOM/user-event/jsdom tests: `DataGrid.tsx` (571 lines), every `*View.tsx`, dialogs, hooks effects (auto-paging loop, abort) have no unit-level behaviour tests; their only coverage is the Playwright specs.
- Weak 2: E2E fixtures seed 2-4 rows per test (`mvp-leads.spec.ts:64-110`). Only 3 hits for load-more/cursor anywhere in the 7 specs. Nothing exercises >50 rows, the 150-row auto-page boundary, the 500 cap, search-over-sample semantics, or "Unknown contact" at scale. This is exactly why F-01/F-02/F-06/F-07 are invisible to the suite: a defect "search finds only 150 of 5,000" passes every test.
- Weak 3: every spec uses a full-rights synthetic manager token, so RBAC-denied states are covered only by forced `page.route` responses (acceptable, but real RBAC-limited reps are not driven except one `rep` assignee). No 401-mid-session, non-secure-context, slow/failed second page, or double-click-on-submit tests.
- Mocks: Playwright forces 409/403 via route interception while using the real server for everything else: good practice, not hiding failures. Unit mocks are limited to fetch/storage injection.
- Not verified by me: the Playwright/DB suites were not executed (section 1). Pass/fail of the 7 mvp specs = unknown.
- Required adds: (a) seed 600+ leads/contacts/tasks via script and assert sample banner, cap, and that "Overdue" equals server `due=overdue` count; (b) jsdom or Playwright component tests for DataGrid search/sort/paging/selection; (c) the first-user path "connect -> land -> create lead -> find it" with 200 existing records.

## 4. Security verdict (SK-008): ACCEPTABLE FOR LOCAL/DEV, not for shared hosting as-is
Assets: bearer token + tenant id (paste gate, D6), CRM PII (names, identifiers behind `sensitive.read`). Actors: user, XSS attacker, LAN observer.
- Token storage: `sessionStorage` (tab-scoped, cleared on close, never localStorage), validated via `GET /v1/session` before persist, never logged (grep: no console.* in `app/src`). Residual: any XSS reads it. Reachable XSS surface found: none (React escaping, no raw HTML sinks, `href`s are built only from internal routes + UUID ids). Hostile record names render as text.
- Saved views in `localStorage` hold only view state keyed by tenant+actor (no tokens/PII beyond filter text, which can include a typed search string): LOW.
- Static serving (`src/static.ts`): strong. Raw-path resolver rejects NUL, backslash, colon, encoded dot/slash, empty/`.`/`..` segments and checks in-root; 20 hostile cases unit-tested. Assets immutable-cached (content-hashed), `index.html` stays `no-store`, `nosniff` is set globally. Unauthenticated asset serving is fine (public bundle). Gap F-18: no `Content-Security-Policy`, `frame-ancestors`/`X-Frame-Options` (token-paste page is frameable: clickjacking), `Referrer-Policy`. Add `default-src 'self'; frame-ancestors 'none'` to `/app` responses (Vite output has no inline script, verify).
- API side (pre-existing): list endpoints use `SELECT *` (crm.ts:657) so every column, including `tenant_id`, is returned; RLS/can_object gates rows but not columns. Acceptable internally; whitelist columns before external exposure.
- Idempotency: correct on the client (key = `command_id`, reused on retry, new key when payload changes via `keyFor`); gaps F-10 (secure-context) and F-14 (reporting key vs body). Merge uses one key per preview: OK.
- Tenant isolation: client sends `X-Tenant-ID` from the session; isolation enforced server-side (RLS), UI trusts it correctly; saved views and overlays are per-mount/per-tenant.
- Not tested here: live exploitation, rate limiting, CSRF (bearer header, so low), CORS (collector only).

## 5. Architecture verdict and API prerequisites (SK-005, SK-012)
Verdict: D3 (client-side only, no API change) is a valid DEMO/prototype tactic and was a reasonable reversible choice for an unattended overnight build, but it is NOT viable for a real CRM. It makes the product's correctness depend on dataset size (150-500 rows) and hides that behind a banner. D1/D2 (Vite+React+TS, handoff layout) and the pure `gridModel` layer are sound and reusable: `computeView` is already isolated, so a server-driven adapter can replace it without redoing screens.
Recommendation: stop adding UI slices (S9-S12). Do one bounded API tranche first, then re-point the cursor lists at query-parameterised fetchers.
P0 (without these the product is not credible; all are additive/backward compatible):
1. Server list query: `q` (text + identifier digest), `sort` (whitelisted) + `dir`, `limit` (<=200), filters (`status`, `owner_id`, `stage_id`, `pipeline_id`, `contact_id`, `due`, `created_since`), keyset cursor on (sort key, id). Today only `cursor` and `tasks?due=` exist (crm.ts:466,643-654).
2. Timestamps: `created_at`/`updated_at` on contact, deal, task (lead has only `received_at`); default order newest-first. Current id order is random UUIDv4, so "recent" is unrepresentable.
3. Embedded names: `expand=contact,owner` (or `GET /contacts?ids=`) on leads/deals/tasks, and deal/task `contact_name`/`stage_name`. Removes F-02/F-11.
4. List envelope: `has_more` plus `total_count` (exact or capped) so the UI can say "50 of 4,213".
P1:
5. Aggregates: `GET /v1/summary` (counts by lead status, deals by stage x currency, tasks overdue/today, per owner). Enables Dashboard (S10) and honest pipeline totals (F-07).
6. Contact list fields: masked phone/email, company/tags; `/session` sensitive-data flag (G7).
7. Activity timeline + notes: unified per-record timeline (notes, calls, stage moves, task events). Today `journey` returns M2 business events and `audit` is admin-only, so there is no "log a note/call" at all. This is the biggest competitive gap after search.
8. Batch commands (bulk assign/complete) with per-item results; field-level 422 details (G3); nullable lead owner (G2); task `source`/`lead_id` (G10).
P2: CSV import endpoint, server-side saved views, currency exponent metadata, ETag/If-None-Match on directories, webhooks.
No-API quick wins to do now: use existing `tasks?due=` (F-06); resolve missing contacts via `GET /contacts/{id}`; relabel sample-bound controls.
