Base: `feat/crm-mvp-ui` @ a81f074 (P1a S1-S5 + security fixes merged; latest migration = 009). Source of truth: ADR-002 (§4, §5 P1b row, §7 answers 1-5 accepted, §9.1 binding). ## 1. Scope recap
1. Property registry (groups, definitions, option sets) per object for contact/lead/deal/task; standard columns exposed as system properties; custom values in a `custom jsonb` column (ADR Option D). No per-tenant DDL.
2. Schema API + manager-only (MFA) property settings; record create/patch accepts `properties:{key:value}` through ONE validator (types, required, read_only, sensitive, limits), reusing `version`, `evidence()`, `durable()`.
3. The P1a list compiler becomes registry-driven: filter/sort/search/projection over custom properties, typed ops, keyset cursor, `fp` includes `schema_rev`.
4. Server saved views (private/shared/default) replacing localStorage; one-time import.
5. Performance gate and index management (`indexed` properties via privileged owner-only tooling).
**OUT:** custom objects, associations, `record` table, `unique`, value history, board/group-by (P2); formulas, rollups, conditional required, configurable lead status (P3); aggregate/chart endpoints (roadmap step 2); glass, Tailwind, blanket React Aria, UI polish pass (roadmap step 4); import/export; url type; sensitive/phone/email as custom types.

## 2. S10 performance thresholds (proposal for the gate before B1)
### 2.1 Target data sizes per tenant (ESTIMATES, from ADR §1 driver (e): 50k typical, 1M ceiling)
| Item | Typical | Ceiling (gate) | Spike seed |
|---|---|---|---|
| Rows, hot object (contact) | 50k | 1M | 50k and 1M (one whale tenant + 50 small tenants of 20k, so the table is ~2M rows and tenant selectivity is realistic) |
| Rows, lead / deal / task | 50k / 30k / 100k | 1M / 500k / 2M | 50k each at the 50k tier; deal 500k only if contact passes |
| Custom properties per object | 20 | 100 (ADR cap) | 20 (main) and 100 (wide variant, 50k rows, TOAST check) |
| Fill rate / avg `custom` size | 60% / ~1.5 KB | 32 KB cap | 60%; 1.5 KB and ~8 KB |
| Values per whale tenant | 50k x 20 x 0.6 = 0.6M | 1M x 20 x 0.6 = 12M | same |
| Options per select / multi-select members | 20 / 1-3 of 12 | 200 / 50 | 20 skewed (Zipf), 200 once |
| Mix | text 25%, select 25%, number 15%, date 15%, checkbox 10%, multi 10%; half the text values Arabic, half English, some mixed | | same |
Existing local fixture already holds ~26k contacts / ~21k deals (P1A_THREAT_MODEL T6), so the 50k tier is realistic without synthetic extremes; the 1M tier is synthetic.

### 2.2 p95 targets (server-side API time for one page of 50 rows, warm cache, local PG 17 as `crm_runtime` under FORCE RLS; machine and PG settings recorded in the result)
| Operation | 50k rows | 1M rows (indexed where stated) |
|---|---|---|
| List default (`-created_at`, keyset) | <= 100 ms | <= 150 ms (index-backed, size-independent) |
| List, system filters (stage + owner, rep scope) | <= 150 ms | <= 400 ms |
| List with custom-property **filter** (select eq / multi has_any / checkbox, GIN) | <= 300 ms | <= 800 ms |
| List with custom **sort** (number/date/text), no filter | <= 300 ms | <= 1000 ms **with `indexed`**; unindexed: no latency bar, but must finish or return a clean timeout (<5 s), never hang |
| List custom filter + custom sort (indexed) | <= 300 ms | <= 1000 ms |
| `q` search (Arabic-folded contains, incl. custom_search) | <= 300 ms | <= 1000 ms **with trigram**; without it the 5 s timeout risk from the P1a review is expected to materialize (that is what the spike confirms) |
| `include_total` (capped 10001) | <= 300 ms | <= 1000 ms |
| Record GET with `properties` | <= 30 ms | <= 30 ms |
| Record PATCH, 5 properties (validator + merge + evidence + search text) | <= 80 ms | <= 100 ms; 20 concurrent writers on distinct rows: 0 errors, p95 <= 250 ms |
| Schema change: create/edit/archive property, edit options | <= 100 ms, **independent of row count** (registry rows + `schema_rev` only, no DDL, no backfill) | same |
| Schema GET (100 properties) | <= 50 ms, <= 64 KB | same |
| `indexed` flip: `CREATE INDEX CONCURRENTLY` on whale tenant | n/a | <= 120 s; writes during build p95 <= 2x baseline |

### 2.3 Index budget (ESTIMATES)
- Per object table: <= 8 indexes in total including existing ones (today: PK, 2 x 008, 1 x 009, plus FK indexes; P1b adds at most 1 GIN `jsonb_path_ops` on `custom` and 1 trigram GIN on the search columns).
- Per-property expression indexes: <= 5 per object per tenant (ADR), <= 200 per database in P1 (catalog bloat guard).
- Total index bytes for the four object tables <= 1.2x heap bytes; insert throughput with GIN+trigram >= 70% of the no-custom-index baseline; GIN pending list handled (fastupdate on, gin_pending_list_limit left default) and measured.
- Row cost: `custom` TOAST rate and table bloat after 1M updates measured once.

### 2.4 How B0 measures
- **Where:** disposable DB (same recipe as `scripts/create-local-db.ts`, new name, never the dev DB), PG 17, throwaway scripts under `scripts/spike/` (headed THROWAWAY, not promoted, not in `npm test`). No repo migration is written by the spike; it uses a scratch copy of the contact/deal DDL plus `custom jsonb`, `custom_search`, the 008/009 indexes, the real RLS policy text and the 3 P1a definer functions, queried as a NOSUPERUSER/NOBYPASSRLS role (a superuser would skip RLS and hide the per-row cost).
- **Seed:** `generate_series` + `COPY`/batched insert (100k batches), distributions per 2.1, `VACUUM ANALYZE` before measuring. Randomize the filter value on each run (no single cached hot value), plus one skewed-rare and one skewed-common value per property.
- **Queries (the exact SQL shape the B4 compiler will emit, hand-written):** the 9 rows of 2.2 plus rep-scope variants, deep page (cursor at position 500k), `q` contains/prefix with and without `pg_trgm`, `jsonb_typeof`-guarded casts, option-position sort, record PATCH merge (`custom || patch`), 20 concurrent PATCH writers.
- **Method:** `EXPLAIN (ANALYZE, BUFFERS)` for plans (no Seq Scan on the whale tenant for gated indexed queries; RLS shows as InitPlan); latency = >= 100 executions per query per tier, p50/p95/max, 3 runs, take the median of p95; one cold run recorded, not gated.
- **Pass bar:** every row of 2.2 met at 50k; at 1M every row met with the stated indexes; index budget 2.3 met. Output: `audits/<date>/P1B_PERF_SPIKE.md` with raw numbers, plans, machine, limits ("measured on this machine only; not production sizing").
### 2.5 If it fails (ADR §6 reversal triggers, made operational)
| Failure | First response | Escalation / reversal |
|---|---|---|
| Custom filter/sort misses the bar with GIN only | Add expression btree on the hot property (the planned `indexed` path); re-measure | Promote hot property to a typed real column behind the same compiler (no API change) |
| More than 30% of properties (or > 8 per object) need promotion | Stop; ESCALATE_TO_DEEP | Adopt typed-slot columns (`num_1..n`, `txt_1..n`) from Option C for the hot objects; ADR-002 amended; B1 migration rewritten before it ships |
| GIN/trigram write amplification breaks the insert/PATCH bar | Drop trigram on custom_search, keep on display columns only; tune GIN | Index only via expression btrees; q on custom props becomes prefix-only |
| `pg_trgm` not installable on the target host | Normalized prefix search only (`starts_with`) | Decision to the user: substring search needs the extension or an external search engine (new ADR) |
| RLS initplan not stable at 1M (hoist regresses) | Fix policy form on the 4 tables | Block B1 until fixed (security review) |
| Whole model misses even with promotion | ESCALATE_TO_DEEP | Reconsider Option C for contact/deal only |
A pass does not prove production suitability (SK-002); the bench is kept as a re-runnable script and re-run in B6 against the real code path.

## 3. Slice plan (migrations start at 010; 009 is taken)
Recommended order: **B0 -> B1 -> B2 -> B3 -> B4 -> B5 -> B6 -> B7.** B0 goes first, before any migration or write path, because: (1) it freezes the choices that are costly to undo once 010 ships and tenants have data (JSONB vs promoted/typed-slot columns, GIN vs expression indexes, the `custom_search` column, trigram); (2) it needs no registry or API (scratch tables), so it costs M, not L; (3) it closes the one open risk of the P1a review (text search timeout at scale) and re-verifies the RLS hoist at 1M; (4) it is server-only, touches no app file, and can run in a parallel session from day 1; (5) a reversal found now rewrites a design doc, found after B3 it rewrites a write path. The second half of ADR S10 (owner-only index function, re-run on real code) stays last (B6) because it needs the compiler.

## 6. Risks (ranked) and security notes
| # | Risk | Mitigation |
|---|---|---|
| 1 | **Scale/performance**: JSONB sort/filter at 1M, `q` timeout (open from P1a review), GIN/trigram write amplification | B0 first with explicit bars (§2) and operational reversal table (§2.5); `indexed` path; 5 s timeout kept; capped totals; B6 re-proof on real code |
| 2 | **Custom-value leak / isolation**: `custom` returned by default, sensitive properties readable via filter/sort/q oracle, RLS missing on a new table, key injection into expressions or index DDL | `custom` never in default `COLUMNS`; `props=` allow-list from registry minus unreadable; compiler rejects sensitive for filter/sort/q; registry-map-only keys + regex + `format(%I,%L)`; two-tenant tests per new table; generic catalog test for RLS+FORCE on every `crm` table and no PUBLIC EXECUTE on definers |
| 3 | **Dynamic UI cost**: DataGrid (977 lines) is built for static columns; dynamic columns, typed filters and an async server views store touch its core | Contract-first, UI one slice behind server; schema -> `ColumnDef`/`ServerSpec` adapter in a new file rather than editing the grid; static grids stay as fallback; B4 before B5 |
| 4 | **Write-path correctness**: lost updates, `schema_rev` race (property archived mid-request), validator drift, merge semantics | Single `validateProperties`; `schema_rev` compared inside the transaction; record `version` covers custom writes; golden vectors; concurrent-PATCH test |
| 5 | **Migration/ops**: hand-listed runner, CHECK on `ADD COLUMN` scanning big tables, no `pg_dump` in this environment (forward-fix only), trigram extension availability, CONCURRENTLY outside the transaction | NOT VALID + VALIDATE; rehearse on a copy of the 26k-row fixture; indexes/extension in their own migration (013) and admin CLI; row-count assertion kept; backup step as in P1a note |
| 6 | **AR/RTL and user-authored text**: property/option labels and values are free text (mixed AR/EN), fallback when one language is missing | `BidiText`/`Bdi` for every user-authored label and value (existing helper); label fallback rule (other language if one missing); AR+EN+RTL Playwright cases in every UI slice |
Security notes: every new table ENABLE+FORCE RLS with the initplan `tenant_boundary`, composite tenant FKs, no DELETE grant (archive only); every SECURITY DEFINER/admin function `SET search_path`, `REVOKE ALL FROM PUBLIC` explicitly (the 008 lesson), runtime EXECUTE only where the API needs it, seed/index functions not granted to runtime; validation lives in one module (`properties.ts` for values, `schema.ts` for definitions, planList for queries); audit `changed_fields` carries keys, never values; agency grants and worker get no property/view actions; new permissions follow the fixed catalogue (no ACL engine); each slice ends with the isolation suites green; a review gate (SK-008 style) before merge of B1, B3, B4, B6.
